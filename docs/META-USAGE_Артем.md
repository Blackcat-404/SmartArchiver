## 1. Запис бітів у буфер (BitWriter)

**Задача.** Організувати потоковий бітовий запис у пам'ять за схемою MSB-first та коректно доповнити останній байт нулями до повної байтової межі під час фіналізації стисненого блоку.

**Промпт:**

> Я пишу клас `BitWriter` для запису стиснених даних Гаффмана у `MemoryStream`. Потрібно писати біти від старшого до молодшого (MSB-first).
> 
> 
> Як правильно реалізувати методи `WriteBits` і `Flush`, щоб біти накопичувалися в буфері та скидалися в потік побайтово, а в кінці добивалися нулями?
> 
> 

**Відповідь:**

При роботі з побітовим потоком у пам'яті фізична одиниця запису завжди залишається байтом (8 біт). Відповідно, нам потрібен внутрішній накопичувальний регістр (`_current`) та лічильник кількості бітів, які вже знаходяться в цьому регістрі (`_filled`).

Метод `WriteBits` розбирає вхідне число `value` від найстаршого біта (індекс `length - 1`) до наймолодшого (індекс `0`). Кожен витягнутий біт додається до правого краю регістра після зсуву ліворуч. Щойно регістр накопичує рівно 8 біт, поточний байт скидається в базовий потік `MemoryStream`, а лічильники обнуляються.

Оскільки загальна довжина закодованого блоку рідко кратна 8 бітам, метод `Flush` виконує обов'язкове доповнення (padding): залишок бітів у регістрі зсувається вліво на невикористану відстань `8 - _filled`, тим самим заповнюючи молодші позиції строго нулями, після чого неповний байт остаточно записується в потік.

```csharp
public void WriteBits(uint value, int length)
{
    for (int k = length - 1; k >= 0; k--)
    {
        _current = (_current << 1) | (int)((value >> k) & 1);
        if (++_filled == 8)
        {
            _output.WriteByte((byte)_current);
            _current = 0;
            _filled = 0;
        }
    }
}

public void Flush()
{
    if (_filled == 0)
        return;

    _output.WriteByte((byte)(_current << (8 - _filled)));
    _current = 0;
    _filled = 0;
}

```

## 2. Швидке читання бітів без алокацій (BitReader)

**Задача.** Створити високопродуктивний читач бітового потоку поверх неперервного масиву байтів без створення об'єктів у керованій купі та забезпечити перевірку раптового обриву даних.

**Промпт:**

> Як зробити `BitReader` на базі `ref struct` над `ReadOnlySpan<byte>`, щоб він читав біти MSB-first прямо зі зрізу пам'яті і кидав помилку `ArchiveException(ErrorCode.E_PAYLOAD)`, якщо потік обірвався раніше, ніж очікувалося?
> 
> 

**Відповідь:**

Для розпакування критично важливо мінімізувати навантаження на Garbage Collector. Оголошення типу як `ref struct` гарантує, що екземпляр завжди буде розташовуватися виключно на стеку. Робота поверх `ReadOnlySpan<byte>` дозволяє парсити довільний зріз закодованого масиву без копіювання байтів.

Структура відстежує поточний індекс зчитування байтів `_next`, поточний розпакований байт `_current` та лічильник залишкових бітів `_left`.

Коли `_left == 0`, метод `ReadBit()` намагається прочитати наступний байт. Якщо покажчик `_next` вже дійшов до або перевищив розмір вхідного зрізу `_data.Length`, це означає, що потік бітів несподівано закінчився, а корисні дані для декодування ще потрібні. У такому разі викидається `ArchiveException` з кодом `ErrorCode.E_PAYLOAD`. Якщо ж байти ще є, завантажується черговий байт, виставляється лічильник `_left = 8`, і старший біт витягується зсувом праворуч.

```csharp
public int ReadBit()
{
    if (_left == 0)
    {
        if (_next >= _data.Length)
            throw new ArchiveException(ErrorCode.E_PAYLOAD, "Потік коду обірвано.");

        _current = _data[_next++];
        _left = 8;
    }

    _left--;
    return (_current >> _left) & 1;
}

```

## 3. Перевірка відсутності зайвих даних у кінці потоку

**Задача.** Забезпечити сувору валідацію цілісності формату: переконатися, що після вичитування всіх розпакованих символів у блоці не лишилося сторонніх байтів або сміття у хвості останнього байта.

**Промпт:**

> Як у `BitReader` реалізувати метод перевірки, що після закінчення читання корисних даних у залишку поточного байта записані виключно нулі і після нього немає зайвих байтів?
> 
> 

**Відповідь:**

При розпакуванні архіву декодер наперед знає, скільки оригінальних символів `rawLength` він має відновити. Після вичитування рівно такої кількості символів у бітовому потоці може залишатися кілька невикористаних бітів до кінця останнього байта. Згідно зі специфікацією запису, ці біти мають бути строго нульовими, а за межами цього байта не повинно бути жодного байта.

Для реалізації методу `EnsureOnlyPaddingLeft` формується динамічна бітова маска `padMask`. Якщо в поточному байті залишилося `_left` бітів, маска `(1 << _left) - 1` виділяє саме ці молодші розряди. Якщо побітове `И` між `_current` та цією маскою дає ненульовий результат, це свідчить про наявність сміття у хвості або зсув потоку. Аналогічно, якщо покажчик `_next` не дійшов точно до `_data.Length`, це означає наявність зайвих хвостових байтів. Обидві умови порушують специфікацію та генерують помилку `ErrorCode.E_PAYLOAD`.

```csharp
public readonly void EnsureOnlyPaddingLeft()
{
    int padMask = _left == 0 ? 0 : (1 << _left) - 1;
    if ((_current & padMask) != 0 || _next != _data.Length)
        throw new ArchiveException(ErrorCode.E_PAYLOAD, "Зайві біти або байти після даних.");
}

```

## 4. Перевірка рівності Крафта для канонічних довжин

**Задача.** Реалізувати швидку цілочисельну валідацію довжин кодів без використання операцій з рухомою комою, а також правильно обробити межовий випадок виродженого алфавіту.

**Промпт:**

> Як цілочисельно перевірити рівність Крафта для масиву довжин коду з максимальною довжиною 15 біт, і як окремо обробити вироджений випадок, коли символ в алфавіті лише один?
> 
> 

**Відповідь:**

Префіксний код вважається коректним і повним, якщо для набору довжин його кодів виконується рівність Крафта: $\sum 2^{-len} = 1$. Оскільки операції з числами з рухомою комою (`double`/`float`) можуть накопичувати похибки округлення, перевірку слід виконувати в цілих числах.

Для обмеження максимальної довжини в 15 біт вся рівність множиться на $2^{15}$. Тоді внесок кожного символу довжини $len$ дорівнює точно `1L << (15 - len)`. Якщо сумарне значення відрізняється від `1L << 15`, дерево або не є повним, або перевантажене і не може бути префіксним.

Окрему увагу слід звернути на вироджений випадок, коли файл складався з повторення одного-єдиного байта. Для одного символу неможливо побудувати звичайне бінарне дерево з двома гілками, тому сума Крафта склала б $2^{-1} = 0.5 \ne 1$. Формат архіву вимагає спеціального правила: якщо унікальний символ рівно один, його довжина обов'язково повинна дорівнювати 1, а код призначається рівним 0.

```csharp
if (used == 1)
{
    if (onlyLength != 1)
        throw new ArchiveException(ErrorCode.E_CODE, "Для одного символу довжина коду має бути 1.");
}
else
{
    long kraft = 0;
    for (int len = 1; len <= MaxCodeLength; len++)
        kraft += (long)count[len] << (MaxCodeLength - len);

    if (kraft != 1L << MaxCodeLength)
        throw new ArchiveException(ErrorCode.E_CODE, "Порушена рівність Крафта.");
}

```

## 5. Генерація числових канонічних кодів із довжин

**Задача.** Розібратися в алгоритмі обчислення числових префіксних кодів за масивом довжин, щоб кодер і декодер формували повністю ідентичні коди.

**Промпт:**

> Маючи масив кількості символів для кожної довжини `count`, як обчислити стартові коди `nextCode` для кожної довжини і присвоїти їх символам у канонічному порядку?
> 
> 

**Відповідь:**

Канонічний код Гаффмана вирішує головну проблему стиснення: позбавляє від необхідності зберігати повну геометрію дерева. Замість цього використовується математичне правило генерації:

1. Коди довжини 1 починаються з нуля.


2. Стартовий код для наступної довжини `bits` утворюється додаванням кількості кодів попередньої довжини `count[bits - 1]` та зсувом на 1 біт ліворуч (тобто множенням на 2).


3. Коли базові значення `nextCode` пораховані, ми проходимо за списком символів від 0 до 255: якщо символ присутній, йому призначається поточне значення `nextCode[len]`, а потім цей лічильник інкрементується на 1.



Такий підхід автоматично забезпечує важливі властивості: коди однакової довжини зростають відповідно до зростання байтових індексів символів, а жоден коротший числовий код не стає числовим префіксом довшого коду.

```csharp
var nextCode = new uint[MaxCodeLength + 1];
uint code = 0;
for (int bits = 1; bits <= MaxCodeLength; bits++)
{
    code = (code + (uint)count[bits - 1]) << 1;
    nextCode[bits] = code;
}

var codes = new uint[lengths.Length];
for (int symbol = 0; symbol < lengths.Length; symbol++)
{
    int len = lengths[symbol];
    if (len != 0)
        codes[symbol] = nextCode[len]++;
}

```

## 6. Детермінована черга пріоритетів для дерева Гаффмана

**Задача.** Усунути недетермінізм у роботі черги з пріоритетом при побудові класичного дерева Гаффмана, коли декілька вузлів мають абсолютно однакову вагу.

**Промпт:**

> При побудові дерева через чергу пріоритетів вузли з однаковою частотою можуть діставатися в довільному порядку. Як спакувати вагу та індекс вузла в один ключ сортування, щоб черга працювала детерміновано?
> 
> 

**Відповідь:**

При класичній побудові дерева Гаффмана два вузли з мінімальними частотами витягуються з `PriorityQueue` і об'єднуються в один батьківський вузол. Однак якщо кілька вузлів мають однакові частоти, стандартна черга в .NET не гарантує стабільного порядку їх вилучення (це залежить від внутрішнього стану бінарної купи). Якщо порядок порушиться, глибини листків можуть вийти різними на різних платформах, що призведе до розбіжності таблиць довжин.

Для забезпечення абсолютної детермінованості вага та порядковий індекс вузла упаковуються в одне 64-бітне число `long`. Вага вузла зміщується на 20 бітів ліворуч, а в молодші 20 бітів записується порядковий індекс вузла. Оскільки в дереві для 256 символів створюється щонайбільше $2 \times 256 - 1 = 511$ вузлів, 20 бітів із запасом вистачає для збереження унікального номера. Черга завжди порівнюватиме спочатку ваги, а при рівності ваг — віддаватиме пріоритет вузлу з меншим індексом.

```csharp
private static long Key(long weight, int index) => (weight << 20) | (uint)index;

```

## 7. Обмеження довжини кодів до 15 біт масштабуванням частот

**Задача.** Забезпечити жорстке дотримання обмеження максимальної глибини дерева (15 біт) за допомогою безпечної евристики масштабування ваг.

**Промпт:**

> Що робити в `HuffmanLengths`, якщо алгоритм побудував дерево з максимальною довжиною коду більше 15 біт? Як зменшити довжину коду за допомогою простого перерахунку частот?
> 
> 

**Відповідь:**

Специфікація формату обмежує довжину будь-якого коду 15 бітами, щоб таблиці розпакування поміщалися в швидку пам'ять і не вимагали 32-бітних регістрів бітового читання. Проте на специфічних розподілах частот (наприклад, експоненційне зростання за числами Фібоначчі) стандартне дерево вироджується в довгий ланцюг глибиною 19–20 рівнів.

Найбільш надійний та алгоритмічно простий підхід полягає в масштабуванні частот (weight scaling). Якщо максимальна глибина листка у збудованому дереві перевищила 15, ми не намагаємося складно перебалансовувати дерево на місці. Замість цього всі ненульові частоти діляться навпіл з додаванням одиниці для захисту від обнулення: `(work[i] + 1) / 2`.

При діленні частоти поступово стискаються в бік 1. Коли всі частоти стають однаковими, дерево стає ідеально збалансованим бінарним деревом з глибиною $\lceil \log_2 256 \rceil = 8$, що гарантовано менше за 15. Таким чином, цикл масштабування завжди успішно завершується за кілька ітерацій і видає валідний набір довжин.

```csharp
while (true)
{
    byte[] lengths = BuildUnlimited(work);

    int maxLength = 0;
    foreach (byte len in lengths)
        if (len > maxLength) maxLength = len;

    if (maxLength <= CanonicalHuffman.MaxCodeLength)
        return lengths;

    for (int i = 0; i < work.Length; i++)
        if (work[i] > 0)
            work[i] = (work[i] + 1) / 2;
}

```

## 8. Підготовка таблиць декодування за збереженими довжинами

**Задача.** Сформувати масиви швидкого доступу для декодера безпосередньо зі збережених 256 байтів довжин без відновлення об'єктів вузлів дерева.

**Промпт:**

> Декодер отримує 256 байтів довжин кодів. Як швидко без побудови об'єктного дерева згрупувати символи в масив `symbols` за зростанням їхніх довжин?
> 
> 

**Відповідь:**

Для розпакування канонічного Гаффмана нам не потрібні структури `Node` з вказівниками `Left` та `Right`. Достатньо знати, які символи відповідають кожній довжині коду, і в якому порядку вони розташовані.

Підготовка виконується за кілька лінійних проходів:

1. Підраховується масив `count`, де індекс — це довжина коду від 1 до 15, а значення — кількість символів, які мають таку довжину.


2. Обчислюється масив префіксних сум `offset`: він визначає стартову позицію в загальному списку символів для кожної довжини.


3. Масив `next` копіює початкові зміщення. Під час фінального проходу по вихідних 256 довжинах кожен символ записується в масив `symbols` за своєю поточною позицією `next[len]++`.



У результаті масив `symbols` містить усі активні байти блоку, ідеально згруповані: спочатку всі символи довжини 1, потім довжини 2, і так далі в алфавітному порядку.

```csharp
var offset = new int[CanonicalHuffman.MaxCodeLength + 2];
for (int len = 1; len <= CanonicalHuffman.MaxCodeLength; len++)
    offset[len + 1] = offset[len] + count[len];

var symbols = new int[TableSize];
var next = (int[])offset.Clone();
for (int s = 0; s < TableSize; s++)
{
    int len = lengths[s];
    if (len != 0)
        symbols[next[len]++] = s;
}

```

## 9. Табличне зчитування окремого символу з потоку

**Задача.** Зрозуміти логіку побітового розпізнавання символу в методі `DecodeSymbol` за допомогою числових меж канонічних префіксів.

**Промпт:**

> Як розпакувати один символ з `BitReader` за допомогою масивів `count` і `symbols`, перебираючи довжину від 1 до 15 біт?
> 
> 

**Відповідь:**

Алгоритм декодування канонічного коду працює без спуску по графу. Він перевіряє гіпотези довжини від $len = 1$ до 15:

На кожній ітерації зчитується один біт і додається до акумулятора `code`. Змінна `first` зберігає найменше значення числового коду для поточної довжини. Якщо зчитаний числовий префікс менший, ніж `first + count[len]`, це означає, що ми знайшли повний валідний код довжини `len`.

Різниця `code - first` показує порядковий номер знайденого символу серед усіх символів цієї довжини. Додаючи його до базового зміщення `index`, ми за одну операцію дістаємо оригінальний байт з масиву `symbols`. Якщо ж поточний префікс виходить за межі `count[len]`, ми переходимо до наступного біта: значення `first` та `code` зсуваються ліворуч, а базовий індекс `index` збільшується на кількість пройдених символів.

```csharp
private static int DecodeSymbol(ref BitReader reader, int[] count, int[] symbols)
{
    int code = 0;
    int first = 0;
    int index = 0;

    for (int len = 1; len <= CanonicalHuffman.MaxCodeLength; len++)
    {
        code |= reader.ReadBit();
        int c = count[len];
        if (code < first + c)
            return symbols[index + (code - first)];

        index += c;
        first = (first + c) << 1;
        code <<= 1;
    }

    throw new ArchiveException(ErrorCode.E_PAYLOAD, "Некоректний код у потоці.");
}

```

## 10. Перевірка префіксності кодів у unit-тестах

**Задача.** Реалізувати структурну перевірку в тестах: підтвердити, що жоден згенерований алгоритмом канонічний код не є префіксом будь-якого іншого коду.

**Промпт:**

> Як у xUnit перевірити властивість префіксності для масиву канонічних кодів Гаффмана, зсуваючи довший код на різницю довжин?
> 
> 

**Відповідь:**

Щоб перевірити префіксність множини бітових послідовностей, необхідно попарно порівняти всі активні символи $a$ та $b$.

Якщо довжини збігаються (`lengths[a] == lengths[b]`), їхні коди повинні просто не дорівнювати один одному.

Якщо ж довжина $a$ строго менша за довжину $b$, код символу $b$ потенційно може починатися з коду $a$. Оскільки ми записуємо біти старшими вперед (MSB-first), префікс довшого коду $b$ знаходиться в його найстарших бітах. Зсунувши значення `codes[b]` праворуч на різницю `lengths[b] - lengths[a]`, ми відкидаємо «хвіст» і залишаємо тільки префікс довжини `lengths[a]`. Якщо цей префікс дорівнює `codes[a]`, властивість префіксності порушена, і однозначне декодування стає неможливим.

```csharp
if (lengths[a] == lengths[b])
{
    Assert.NotEqual(codes[a], codes[b]);
}
else
{
    // Відкидаємо молодші біти і порівнюємо префікс
    Assert.NotEqual(codes[a], codes[b] >> (lengths[b] - lengths[a]));
}

```

>

**Відповідь:**

Якщо частоти символів зростають як послідовність Фібоначчі ($F_n = F_{n-1} + F_{n-2}$), кожна нова сума двох менших елементів виявляється рівною наступному елементу ряду. Через це дерево не розгалужується рівномірно, а перетворюється на вироджений однобічний бамбук, де глибина кожного наступного листка на 1 більша за попередній. 2. Після застосування скоригованих довжин повний цикл кодування та декодування (`AssertRoundTrip`) повертає вихідний масив байтів без спотворень.



```csharp
var freq = new long[256];
long a = 1, b = 1;
for (int i = 0; i < 20; i++)
{
    freq[i] = a;
    (a, b) = (b, a + b);
}

byte[] lengths = HuffmanLengths.Build(freq);
Assert.True(lengths.Max() <= CanonicalHuffman.MaxCodeLength);

var data = new List<byte>();
a = 1; b = 1;
for (int i = 0; i < 20; i++)
{
    for (long k = 0; k < a; k++) data.Add((byte)i);
    (a, b) = (b, a + b);
```

## 12. Мутаційне тестування інверсією бітів

**Задача.** Переконатися, що декодер захищений від аварійних падінь платформи при отриманні пошкоджених файлів і завжди викидає лише очікуваний доменний виняток `ArchiveException`.

**Промпт:**

> Як написати цикл для тесту, який по черзі інвертує біти в кожному байті валідного архіву масками `0x01`, `0x80`, `0xFF` і очікує лише `ArchiveException`?
> 
> 

**Відповідь:**

Однією з головних вимог надійності до архіватора є безпека при читанні пошкоджених архівів. Навіть якщо біти стисненого потоку пошкоджені, внутрішні методи декодера не повинні призводити до аварійних системних збоїв на кшталт `IndexOutOfRangeException` (вихід за межі буфера) чи `NullReferenceException`.

Мутаційний тест бере повністю валідний закодований блок і послідовно проходить по кожному його байту. Для кожного байта застосовуються три типи спотворень: інверсія молодшого біта (`0x01`), інверсія старшого біта (`0x80`) та повна інверсія байта (`0xFF`). Отриманий масив передається в `Decode` всередині блоку `try / catch (ArchiveException)`.

Якщо метод успішно декодує дані або коректно відхилить їх через контрольований `ArchiveException`, ітерація вважається успішною. Якщо ж вилетить будь-який інший виняток середовища виконання, `catch` його пропустить, і тест автоматично завалиться, вказавши на місце вразливості.

```csharp
foreach (int index in Enumerable.Range(0, original.Length))
{
    foreach (byte mask in new byte[] { 0x01, 0x80, 0xFF })
    {
        byte[] mutated = (byte[])original.Clone();
        mutated[index] ^= mask;

        try
        {
            HuffmanCodec.Decode(mutated, data.Length);
        }
        catch (ArchiveException)
        {
            // Очікувана контрольована відмова
        }
    }
}

```

```csharp

{
    tokens.Add(Lz77Token.Match(distance, length));
    for (int k = 0; k < length; k++)
        finder.Insert(pos + k);

else
{
```

Цей фрагмент допоміг зрозуміти основну ідею Greedy: або записуємо збіг, або один байт. Позиції збігу додаються до історії пошуку для наступних кроків.

**Промпт:**

**Відповідь:**

Було пояснено, що Lazy порівнює збіг у поточній і наступній позиціях. Якщо наступний суттєво довший, алгоритм записує літерал зараз, щоб використати довше посилання далі. Окремо розібрали невдалий тест, у якому вхідний рядок не створював очікуваного збігу; після виправлення тести пройшли.

```csharp
    finder.TryLongest(pos + 1, out _, out int nextLength))
```

Тут я розібрався, що `minLazyGain` — це поріг, за яким алгоритм вирішує зачекати один байт і взяти вигідніший збіг на наступній позиції.

## 20. Наскрізне тестування корпусу та CRC32

**Задача.** Переконатися, що після стискання, створення архіву та розпакування дані залишаються незмінними для всіх семи груп корпусу.

**Промпт:**

> Як правильно організувати інтеграційний тест для архіватора, щоб він перевіряв не лише роботу окремого кодека, а повний цикл `ArchiveWriter` → `ArchiveReader`? Хочу пройти всі групи тестових файлів, порівняти відновлені байти й перевірити CRC32.

Для перевірки цілого архіватора потрібен **наскрізний round-trip**: `ArchiveWriter` створює архів, `ArchiveReader` відкриває його, після чого ти зіставляєш кожен відновлений файл з оригіналом. Так перевіряються одночасно вибір стратегії, межі блоків, Huffman-таблиці, порядок блоків і таблиця файлів. Якщо в будь-якій із цих частин є помилка, простий unit-тест `Lz77BlockEncoder` її не побачить.

Рекомендую перебрати всі каталоги `Datasets/0`–`Datasets/6` й усі файли в кожному каталозі. Перевіряй не лише вміст, а й кількість та імена файлів: архів може відновити правильні байти під неправильним іменем. Окремо перевір два способи формування блоків — фіксований та DP — і випадки, коли невигідний для стиснення блок зберігається як `Stored`. Для кожного файла використовуй `Assert.Equal` над повними масивами байтів.

CRC32 є додатковою перевіркою цілісності. Порівняй CRC32 оригінального й відновленого вмісту, але **не замінюй ним побайтове порівняння**: різні файли теоретично можуть мати однакову контрольну суму. Оскільки тест використовує класи `ArchiveWriter` і `ArchiveReader`, його логічне місце — тестова збірка Archive, навіть якщо початковий файл із тестами зберігається в теці Compression.Tests.

**Фрагмент коду, який розбирали:**

```csharp
// Схема перевірки після створення й читання архіву.
foreach (var original in inputFiles)
{
    byte[] restored = restoredFiles[original.Name];
    Assert.Equal(original.Bytes, restored);
    Assert.Equal(Crc32.Compute(original.Bytes), Crc32.Compute(restored));
}
```
## 21. Ітеративний DP з урахуванням кодів Huffman

**Задача.** Поліпшити фіксований DP-розбір LZ77, щоб рішення про вибір літерала або збігу враховувало фактичні довжини кодів Huffman.

**Промпт:**

> У мене вже є `DpParser`, який рахує вартість літерала як 9 біт, а посилання — за фіксованою формулою. Як зробити ітеративну оптимізацію: побудувати Huffman за початковими токенами, перерахувати їхню вартість і повторити DP? Як зберегти сумісність зі старими викликами парсера?

**Відповідь:**

Фіксований DP мінімізує умовну вартість токенів: літерал має ціну 9 бітів, а посилання — `17 + max(0, bit_length(dist - 1) - 1)`. Це корисна початкова оцінка, але вона не дорівнює ціні токенів після Huffman. Наприклад, частий літерал може отримати дуже короткий код, а рідкісний — довший. Отже, вибір найменшого за фіксованою моделлю набору токенів не гарантує мінімального реального блока.

Для ітеративної оптимізації спочатку отримай токени звичайним DP і закодуй їх через `Lz77BlockEncoder`. За частотами отриманих символів побудуй таблиці Huffman для `LIT`, `LEN` і `DIST`. Створи `ParseCostModel`, яка враховує довжини цих кодів та додаткові біти відстані. Потім повтори DP із новими цінами. Важливо враховувати **окремі Huffman-символи відстаней**, навіть коли кількість додаткових бітів у двох класів однакова.

Після кожного проходу кодуй токени в справжній блок і порівнюй `encoded.Length`. Новий розбір варто приймати тільки тоді, коли він реально коротший: модельна оцінка не враховує всі витрати на заголовки та перебудовані таблиці. Збережи старий виклик `DpParser.Parse(data)` як обгортку над `Parse(data, ParseCostModel.Fixed())`. Таким чином, звичайний DP залишається сумісним із CP2, а ітеративний режим використовує нову модель без зміни архівного формату.

**Фрагмент коду, який розбирали:**

```csharp
// Старий інтерфейс зберігає фіксовану модель вартості.
public static List<Lz77Token> Parse(byte[] block, int maxChain = 256) =>
    Parse(block, ParseCostModel.Fixed(), maxChain);

// Принцип вибору результату в ітеративному парсері.
byte[] candidateEncoded = Lz77BlockEncoder.Encode(candidateTokens);
if (candidateEncoded.Length < bestEncoded.Length)
{
    bestTokens = candidateTokens;
    bestEncoded = candidateEncoded;
}
```
## 22. Оптимізація швидкодії DP та спадання виграшу

**Задача.** Зменшити час роботи ітеративного DP й оцінити, чи виправдані друга та третя ітерації.

**Промпт:**

> Чому повторний DP із вартістю Huffman працює значно повільніше за звичайний розбір? Як уникнути перевірки всіх довжин збігів у кожній позиції та виміряти додаткову економію після кожного повторення?

**Відповідь:**

Основне джерело повільної роботи — багаторазова оцінка переходів DP. У кожній позиції алгоритм перебирає можливі LZ77-збіги, а для кожного збігу — допустимі довжини. Якщо кожну довжину перевіряти окремо на кожній ітерації, обсяг роботи швидко зростає разом із `blockSize`, `maxChain` і `maxIterations`.

DP обчислюється від кінця блока до початку. Для переходу довжини `length` його ціна складається з вартості токена та `cost[position + length]`. Якщо частина довжин має однакові складові ціни, скористайся попередньо обчисленими мінімумами на діапазонах замість повторного перебору. Для Huffman-моделі мінімуми потрібно обчислювати з урахуванням ціни **конкретного коду довжини**, а не лише суфікса. Так можна зменшити кількість однакових операцій, не змінюючи принципу оптимізації.

Для дослідження спадання виграшу реєструй ітерацію `0` як базовий DP, а для наступних — реальну економію байтів і час виконання. На корпусі з 22 файлів в одному із запусків із блоками 8 КіБ та `maxChain = 32` початковий DP займає **231 592 Б**, а три проходи дають економію **960, 183 і 25 Б** відповідно. Разом це **1 168 Б (0,50%)**, а підсумковий розмір — **230 424 Б**. Такий спад показує, чому безмежне повторення DP невигідне. Для чесного порівняння швидкості завжди фіксуй однакові параметри запуску.

**Фрагмент коду, який розбирали:**

```csharp
// Підсумовуємо виграш кожної ітерації по всіх блоках.
var gains = report.Iterations
    .GroupBy(row => row.Iteration)
    .OrderBy(group => group.Key)
    .Select(group => new
    {
        Iteration = group.Key,
        GainBytes = group.Sum(row => (long)row.GainBytes),
        Seconds = group.Sum(row => row.ElapsedSeconds)
    });
```

## 24. Арифметичне кодування як альтернатива Huffman

**Задача.** Реалізувати незалежний експериментальний кодер і порівняти з Huffman ефективність представлення одних і тих самих LZ77-токенів.

**Промпт:**

> Як працює арифметичне кодування та чим воно відрізняється від Huffman? Як порівняти їх чесно, якщо наш LZ77 уже формує літерали, довжини та відстані? Чому треба окремо рахувати payload і службові байти?

**Відповідь:**

Huffman і арифметичне кодування розв'язують одну задачу — компактно подають послідовність символів, — але роблять це по-різному. Huffman призначає кожному символу префіксний код цілої довжини в бітах. Арифметичне кодування поступово звужує числовий інтервал відповідно до ймовірностей символів, тому середня вартість символу не обмежується цілою кількістю бітів. На певних розподілах це дозволяє отримати менший **payload** — сам закодований потік.

Щоб порівняння було чесним, передай обом кодерам **однакові LZ77-токени**. Тоді різницю визначає ентропійне кодування, а не різний пошук збігів. Для сумісності з поточним поданням токенів арифметичний кодер використовує три алфавіти `LIT`, `LEN`, `DIST` і відповідні таблиці частот. Декодер повинен відновити початковий потік та пройти побайтовий round-trip. При цьому експериментальний Arithmetic **не додається в SARC**: справжні архіви продовжують використовувати канонічний Huffman.

Порівнюй два розміри: `payload` і `total`. До `total` входять таблиці, заголовки та сам потік. За продуктових параметрів 64 КіБ / `maxChain = 256` на корпусі з 22 файлів Huffman займає **199 620 Б**, Arithmetic — **201 308 Б**. Проте payload Arithmetic коротший на **1 169 Б**. Отже, сам потік арифметичне кодування представляє компактніше, але його службові таблиці перекривають цю економію. Це і є головний висновок експерименту, а не твердження, що Huffman завжди кращий.

**Результат експерименту** (64 КіБ, `maxChain = 256`, 22 файли): Huffman — **199 620 Б**, Arithmetic — **201 308 Б**. При цьому лише закодований потік у Arithmetic був меншим: **189 478 Б проти 190 647 Б**. Але на таблиці й заголовки Arithmetic витратив 11 830 Б проти 8 973 Б у Huffman.
## 25. Робота з бітовим потоком і виправлення Arithmetic-декодера

**Задача.** Розібратися з передаванням `BitReader` у C# та прибрати непотрібні 32 нульові біти наприкінці арифметичного потоку.

**Промпт:**

> Чому C# може забороняти передавати `ref BitReader` у методи арифметичного декодера, якщо сам `BitReader` є `ref struct`? Як правильно організувати декодер і чи обов'язково записувати додаткові нульові біти в кінець потоку?

**Відповідь:**

`BitReader` працює поверх `ReadOnlySpan<byte>`, тому його тип доцільно оголошувати як `ref struct`: читач не повинен виходити за межі часу життя свого вхідного буфера. Водночас `ArithmeticDecoder` зберігає тільки числові поля стану — межі інтервалу та поточне значення, — тож йому достатньо звичайного `struct`. Якщо метод декодера приймає читач за посиланням, `scoped ref BitReader` показує компілятору, що це посилання не зберігається після завершення виклику. Такий дизайн усуває конфлікт часу життя посилань, який спричиняє `CS8350` і `CS8352`.

Після завершення арифметичного кодування декодер інколи потребує ще кілька бітів для оновлення свого числового стану. Для стандартної схеми арифметичного декодування їх можна трактувати як **віртуальні нулі за межею потоку**, не додаючи фізично 32 нульові біти в кожен блок. Для цього залиш суворий `ReadBit()` для основного архівного кодека й додай окремий `ReadBitOrZero()` для експериментального Arithmetic. У конструкторі арифметичного декодера та при оновленні стану читай біти саме цим методом, а з `Finish()` прибери запис `WriteBits(0, 32)`.

Таке виправлення скорочує арифметичний результат на **4 байти на блок**. Однак віртуальні нулі не є повноцінною перевіркою цілісності: деякі обрізані або пошкоджені потоки можуть вимагати додаткових перевірок довжини й контрольної суми. Тому зберігай тести на неправильні заголовки, обрізаний вхід і точне відновлення, а в продуктовому Huffman-декодері не змінюй суворе читання.

**Фрагмент коду, який розбирали:**

```csharp
// Спеціальний варіант читання для арифметичного кодера.
public int ReadBitOrZero() =>
    (_left == 0 && _next >= _data.Length) ? 0 : ReadBit();

// Використання в декодері замість прямого читання біта:
_value = (_value << 1) | (uint)reader.ReadBitOrZero();
```
## 26. Дослідження компактного представлення частот

**Задача.** Зрозуміти, чи можна зменшити службові витрати арифметичного кодера та чи вплине це на його порівняння з Huffman.

**Промпт:**

> Чому таблиці частот у нашому Arithmetic займають більше місця, ніж канонічні таблиці Huffman? Які є прості способи записувати частоти компактніше, і чи зміниться від цього саме арифметичне кодування?

**Відповідь:**

Розмір повного арифметичного блока складається з payload і службових даних. У нашому статичному Arithmetic для кожного присутнього символу записується `ushort symbol` та `ushort frequency`, тобто **4 байти на пару**. Коли різних символів багато, таблиці `LIT`, `LEN`, `DIST` можуть займати помітну частину результату. У Huffman достатньо передати довжини канонічних кодів, тому службова частина за цих умов менша.

Один із способів оптимізації — `VarInt` для частот: невелике число, наприклад `5` або `100`, займає один байт, а більші значення — декілька. Другий спосіб — бітова маска присутності символів (`Bitmap`), яка дозволяє не записувати двобайтовий номер кожного активного символу. Але маска фіксованого алфавіту може бути невигідною, якщо в ньому присутні лише один-два символи. Тому для дослідницького компактного формату можна порівнювати список активних символів і bitmap та вибирати коротший варіант для кожної таблиці.

Важливо розділяти ці оптимізації та саме арифметичне кодування. За однакових частот і токенів **payload не змінюється**; компактнішими стають лише таблиці. Для фінального варіанта завдання залишай стандартні таблиці: вони простіші, а головна мета — виміряти різницю з Huffman та пояснити її. Компактне подання розглядай як можливе продовження, а не як частину остаточного архівного формату.

**Фрагмент коду, який розбирали:**

```csharp
// Ідея VarInt: молодші 7 бітів у кожному байті,
// старший біт показує, чи є продовження.
while (value >= 0x80)
{
    output.WriteByte((byte)((value & 0x7F) | 0x80));
    value >>= 7;
}
output.WriteByte((byte)value);
```
## 27. Порівняння повних архівів SmartArchiver та ZIP

**Задача.** Перевірити, наскільки власний архіватор наблизився до ZIP за стисненням повного корпусу файлів.

**Промпт:**

> Як правильно порівняти наш архіватор зі звичайним ZIP, якщо формати архівів мають різні заголовки? Які режими SmartArchiver слід перевірити, щоб вибрати найкращий, і чому недостатньо порівнювати тільки LZ77 або Huffman payload?

**Відповідь:**

Для порівняння з ZIP вимірюй **повні архіви**, а не лише LZ77/Huffman payload. Повний SARC включає записи файлів, службові поля блоків та кодовані дані; ZIP має власні заголовки та центральний каталог. Якщо взяти лише стиснений потік одного алгоритму, результат буде нечесним, бо накладні витрати іншого архіватора вже враховані.

Бери той самий корпус із 22 файлів і створюй на ньому ZIP та SARC із кількома режимами: `Lazy / 64 KiB`, `Iterative / 64 KiB`, `Iterative / 128 KiB`, `Iterative / 256 KiB`, `DP Block Split / 64 KiB`. Для кожного режиму вимірюй розмір готового архіву й час створення. Після цього розпакуй кожен архів і перевір точну відповідність кожного файла. Серед SARC-режимів вибирай найменший **фактичний архів**, а не найкращу модельну вартість DP.

У поточному експерименті ZIP, створений через `.NET CompressionLevel.SmallestSize`, має розмір **192 969 Б**, а найкращий SARC (`Iterative / 128 KiB`) — **198 129 Б**, тобто відставання становить **5 160 Б або 2,67% від ZIP**. Це не доказ перемоги над `zip -9`: `.NET SmallestSize` не гарантовано збігається з реалізацією Info-ZIP. У звіті називай саме той інструмент, який запускається в коді.

**Фрагмент коду, який розбирали:**

```csharp
// Обираємо найкомпактніший із реально створених архівів.
var best = configurations.MinBy(result => result.SarcBytes);

long difference = zipBytes - best!.SarcBytes;
double differencePercent = 100.0 * difference / zipBytes;
```

**Результат на 22 файлах** (930 262 Б вихідних даних): ZIP `.NET SmallestSize` — **192 969 Б**, найкращий SmartArchiver `Iterative / 128 KiB` — **198 129 Б**. Різниця — **5 160 Б (2,67%)** від ZIP. При цьому Iterative потребував приблизно 27,54 с, тоді як Lazy / 64 KiB — 0,331 с.
## 28. Розділення відповідальності Compression і CLI та створення ZIP засобами .NET

**Задача.** Розмістити реалізацію бенчмарка у своєму проєкті Compression, не створюючи циклічних залежностей і не встановлюючи сторонню програму для ZIP.

**Промпт:**

> Чи можна тримати `Zip9Benchmark` у `SmartArchiver.Compression`, якщо для перевірки повного SARC потрібен `ArchiveWriter`? Як організувати виклики між проєктами, щоб не виникла циклічна залежність? І чи можна створювати ZIP лише засобами .NET?

**Відповідь:**

Розташовувати `Zip9Benchmark` у проєкті `SmartArchiver.Compression` можна, але слід зберегти правильний напрям залежностей. `ArchiveWriter` належить до Archive й використовує Compression. Якщо змусити Compression напряму викликати Archive, з'явиться циклічне посилання між проєктами. Тому розділи відповідальність: Compression координує бенчмарк і обчислює метрики, а код верхнього рівня передає йому функцію створення справжнього SARC-архіву.

Зручно використовувати делегат або інший невеликий контракт: бенчмарк отримує список файлів і налаштування, викликає передану функцію та приймає розмір і результати перевірки. `ConsoleApp` має доступ до `ArchiveWriter`, тому саме він може передавати реалізацію такого делегата. Це **інверсія залежності**: нижчий модуль знає лише про контракт, а не про вищий проєкт. Сам клас `Zip9Benchmark.cs` при цьому залишається в Compression.

Для ZIP не обов'язково викликати зовнішню програму. `System.IO.Compression.ZipArchive` підтримує `CompressionLevel.SmallestSize` і працює через штатні бібліотеки .NET. Але назва `SmallestSize` означає намір стискати якомога компактніше у вибраній реалізації, а не тотожність зовнішній команді `zip -9`. Через це в заголовку бенчмарка варто писати `ZIP (.NET SmallestSize)` і вказувати точні налаштування.

**Фрагмент коду, який розбирали:**

```csharp
using var stream = new MemoryStream();
using (var zip = new ZipArchive(stream, ZipArchiveMode.Create, leaveOpen: true))
{
    var entry = zip.CreateEntry("sample.bin", CompressionLevel.SmallestSize);
    using var entryStream = entry.Open();
    entryStream.Write(fileBytes);
}
long zipBytes = stream.Length;
```
## 29. Аналіз відставання від ZIP та вибір фінального рішення

**Задача.** Пояснити, чому SmartArchiver стискає різні групи корпусу неоднаково, і вирішити, чи потрібно додавати ще одну адаптивну оптимізацію.

**Промпт:**

> Чому різниця між SARC і ZIP на BMP та бінарних файлах значно більша, ніж на текстових даних? Чи можна покращити результат, пробуючи для кожного файла кілька наших парсерів, і чи варто робити це для бонусного завдання?

**Відповідь:**

Різниця між ZIP та SmartArchiver залежить не стільки від розширення файла, скільки від його структури: кількості повторень, їхніх довжин, відстаней та розподілу символів. Обидва архіватори застосовують LZ77 і Huffman, але використовують різні стратегії пошуку та різне представлення службової інформації. У SmartArchiver пошук кандидатів обмежений `maxChain`, а межі блока впливають на доступні збіги. Тому на певних BMP і бінарних файлах ZIP може краще використати повторення або компактніше описати результат.

Щоб встановити справжню причину відставання, потрібні вимірювання **по кожному файлу**, статистика літералів і збігів та витрат на Huffman-таблиці. Різниці по групах лише вказують, де шукати. У нашому експерименті найбільше відставання спостерігається на групі BMP (**4 772 Б**) і бінарній групі (**2 144 Б**), тоді як на програмному коді SARC виграє **388 Б**, а на JSON/CSV/XML — **1 405 Б**. Ці числа стосуються окремих архівів за групами й не підсумовуються безпосередньо в різницю загального архіву.

Можна перевірити адаптивний вибір найменшого режиму стиснення для кожного файла, однак це потребує додаткових прогонів і часу. Для фінального бонусного дослідження достатньо порівняння вже наявних режимів і чесного висновку: SARC наближається до ZIP на цьому корпусі, але **не обганяє його**. Оскільки еталон створюється через `.NET SmallestSize`, результат не слід підписувати як перемогу або поразку саме від зовнішнього `zip -9`.
