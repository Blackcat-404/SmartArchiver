## 1. Запис бітів у буфер (BitWriter)

**Задача.** Організувати потоковий бітовий запис у пам'ять за схемою MSB-first та коректно доповнити останній байт нулями до повної байтової межі під час фіналізації стисненого блоку.

**Промпт:**

> Я пишу клас `BitWriter` для запису стиснених даних Гаффмана у `MemoryStream`. Потрібно писати біти від старшого до молодшого (MSB-first).
> 
> 
> Як правильно реалізувати методи `WriteBits` і `Flush`, щоб біти накопичувалися в буфері та скидалися в потік побайтово, а в кінці добивалися нулями?
> 
> 

**Відповідь:**

При роботі з побітовим потоком у пам'яті фізична одиниця запису завжди залишається байтом (8 біт). Відповідно, нам потрібен внутрішній накопичувальний регістр (`_current`) та лічильник кількості бітів, які вже знаходяться в цьому регістрі (`_filled`).

Метод `WriteBits` розбирає вхідне число `value` від найстаршого біта (індекс `length - 1`) до наймолодшого (індекс `0`). Кожен витягнутий біт додається до правого краю регістра після зсуву ліворуч. Щойно регістр накопичує рівно 8 біт, поточний байт скидається в базовий потік `MemoryStream`, а лічильники обнуляються.

Оскільки загальна довжина закодованого блоку рідко кратна 8 бітам, метод `Flush` виконує обов'язкове доповнення (padding): залишок бітів у регістрі зсувається вліво на невикористану відстань `8 - _filled`, тим самим заповнюючи молодші позиції строго нулями, після чого неповний байт остаточно записується в потік.

```csharp
public void WriteBits(uint value, int length)
{
    for (int k = length - 1; k >= 0; k--)
    {
        _current = (_current << 1) | (int)((value >> k) & 1);
        if (++_filled == 8)
        {
            _output.WriteByte((byte)_current);
            _current = 0;
            _filled = 0;
        }
    }
}

public void Flush()
{
    if (_filled == 0)
        return;

    _output.WriteByte((byte)(_current << (8 - _filled)));
    _current = 0;
    _filled = 0;
}

```

## 2. Швидке читання бітів без алокацій (BitReader)

**Задача.** Створити високопродуктивний читач бітового потоку поверх неперервного масиву байтів без створення об'єктів у керованій купі та забезпечити перевірку раптового обриву даних.

**Промпт:**

> Як зробити `BitReader` на базі `ref struct` над `ReadOnlySpan<byte>`, щоб він читав біти MSB-first прямо зі зрізу пам'яті і кидав помилку `ArchiveException(ErrorCode.E_PAYLOAD)`, якщо потік обірвався раніше, ніж очікувалося?
> 
> 

**Відповідь:**

Для розпакування критично важливо мінімізувати навантаження на Garbage Collector. Оголошення типу як `ref struct` гарантує, що екземпляр завжди буде розташовуватися виключно на стеку. Робота поверх `ReadOnlySpan<byte>` дозволяє парсити довільний зріз закодованого масиву без копіювання байтів.

Структура відстежує поточний індекс зчитування байтів `_next`, поточний розпакований байт `_current` та лічильник залишкових бітів `_left`.

Коли `_left == 0`, метод `ReadBit()` намагається прочитати наступний байт. Якщо покажчик `_next` вже дійшов до або перевищив розмір вхідного зрізу `_data.Length`, це означає, що потік бітів несподівано закінчився, а корисні дані для декодування ще потрібні. У такому разі викидається `ArchiveException` з кодом `ErrorCode.E_PAYLOAD`. Якщо ж байти ще є, завантажується черговий байт, виставляється лічильник `_left = 8`, і старший біт витягується зсувом праворуч.

```csharp
public int ReadBit()
{
    if (_left == 0)
    {
        if (_next >= _data.Length)
            throw new ArchiveException(ErrorCode.E_PAYLOAD, "Потік коду обірвано.");

        _current = _data[_next++];
        _left = 8;
    }

    _left--;
    return (_current >> _left) & 1;
}

```

## 3. Перевірка відсутності зайвих даних у кінці потоку

**Задача.** Забезпечити сувору валідацію цілісності формату: переконатися, що після вичитування всіх розпакованих символів у блоці не лишилося сторонніх байтів або сміття у хвості останнього байта.

**Промпт:**

> Як у `BitReader` реалізувати метод перевірки, що після закінчення читання корисних даних у залишку поточного байта записані виключно нулі і після нього немає зайвих байтів?
> 
> 

**Відповідь:**

При розпакуванні архіву декодер наперед знає, скільки оригінальних символів `rawLength` він має відновити. Після вичитування рівно такої кількості символів у бітовому потоці може залишатися кілька невикористаних бітів до кінця останнього байта. Згідно зі специфікацією запису, ці біти мають бути строго нульовими, а за межами цього байта не повинно бути жодного байта.

Для реалізації методу `EnsureOnlyPaddingLeft` формується динамічна бітова маска `padMask`. Якщо в поточному байті залишилося `_left` бітів, маска `(1 << _left) - 1` виділяє саме ці молодші розряди. Якщо побітове `И` між `_current` та цією маскою дає ненульовий результат, це свідчить про наявність сміття у хвості або зсув потоку. Аналогічно, якщо покажчик `_next` не дійшов точно до `_data.Length`, це означає наявність зайвих хвостових байтів. Обидві умови порушують специфікацію та генерують помилку `ErrorCode.E_PAYLOAD`.

```csharp
public readonly void EnsureOnlyPaddingLeft()
{
    int padMask = _left == 0 ? 0 : (1 << _left) - 1;
    if ((_current & padMask) != 0 || _next != _data.Length)
        throw new ArchiveException(ErrorCode.E_PAYLOAD, "Зайві біти або байти після даних.");
}

```

## 4. Перевірка рівності Крафта для канонічних довжин

**Задача.** Реалізувати швидку цілочисельну валідацію довжин кодів без використання операцій з рухомою комою, а також правильно обробити межовий випадок виродженого алфавіту.

**Промпт:**

> Як цілочисельно перевірити рівність Крафта для масиву довжин коду з максимальною довжиною 15 біт, і як окремо обробити вироджений випадок, коли символ в алфавіті лише один?
> 
> 

**Відповідь:**

Префіксний код вважається коректним і повним, якщо для набору довжин його кодів виконується рівність Крафта: $\sum 2^{-len} = 1$. Оскільки операції з числами з рухомою комою (`double`/`float`) можуть накопичувати похибки округлення, перевірку слід виконувати в цілих числах.

Для обмеження максимальної довжини в 15 біт вся рівність множиться на $2^{15}$. Тоді внесок кожного символу довжини $len$ дорівнює точно `1L << (15 - len)`. Якщо сумарне значення відрізняється від `1L << 15`, дерево або не є повним, або перевантажене і не може бути префіксним.

Окрему увагу слід звернути на вироджений випадок, коли файл складався з повторення одного-єдиного байта. Для одного символу неможливо побудувати звичайне бінарне дерево з двома гілками, тому сума Крафта склала б $2^{-1} = 0.5 \ne 1$. Формат архіву вимагає спеціального правила: якщо унікальний символ рівно один, його довжина обов'язково повинна дорівнювати 1, а код призначається рівним 0.

```csharp
if (used == 1)
{
    if (onlyLength != 1)
        throw new ArchiveException(ErrorCode.E_CODE, "Для одного символу довжина коду має бути 1.");
}
else
{
    long kraft = 0;
    for (int len = 1; len <= MaxCodeLength; len++)
        kraft += (long)count[len] << (MaxCodeLength - len);

    if (kraft != 1L << MaxCodeLength)
        throw new ArchiveException(ErrorCode.E_CODE, "Порушена рівність Крафта.");
}

```

## 5. Генерація числових канонічних кодів із довжин

**Задача.** Розібратися в алгоритмі обчислення числових префіксних кодів за масивом довжин, щоб кодер і декодер формували повністю ідентичні коди.

**Промпт:**

> Маючи масив кількості символів для кожної довжини `count`, як обчислити стартові коди `nextCode` для кожної довжини і присвоїти їх символам у канонічному порядку?
> 
> 

**Відповідь:**

Канонічний код Гаффмана вирішує головну проблему стиснення: позбавляє від необхідності зберігати повну геометрію дерева. Замість цього використовується математичне правило генерації:

1. Коди довжини 1 починаються з нуля.


2. Стартовий код для наступної довжини `bits` утворюється додаванням кількості кодів попередньої довжини `count[bits - 1]` та зсувом на 1 біт ліворуч (тобто множенням на 2).


3. Коли базові значення `nextCode` пораховані, ми проходимо за списком символів від 0 до 255: якщо символ присутній, йому призначається поточне значення `nextCode[len]`, а потім цей лічильник інкрементується на 1.



Такий підхід автоматично забезпечує важливі властивості: коди однакової довжини зростають відповідно до зростання байтових індексів символів, а жоден коротший числовий код не стає числовим префіксом довшого коду.

```csharp
var nextCode = new uint[MaxCodeLength + 1];
uint code = 0;
for (int bits = 1; bits <= MaxCodeLength; bits++)
{
    code = (code + (uint)count[bits - 1]) << 1;
    nextCode[bits] = code;
}

var codes = new uint[lengths.Length];
for (int symbol = 0; symbol < lengths.Length; symbol++)
{
    int len = lengths[symbol];
    if (len != 0)
        codes[symbol] = nextCode[len]++;
}

```

## 6. Детермінована черга пріоритетів для дерева Гаффмана

**Задача.** Усунути недетермінізм у роботі черги з пріоритетом при побудові класичного дерева Гаффмана, коли декілька вузлів мають абсолютно однакову вагу.

**Промпт:**

> При побудові дерева через чергу пріоритетів вузли з однаковою частотою можуть діставатися в довільному порядку. Як спакувати вагу та індекс вузла в один ключ сортування, щоб черга працювала детерміновано?
> 
> 

**Відповідь:**

При класичній побудові дерева Гаффмана два вузли з мінімальними частотами витягуються з `PriorityQueue` і об'єднуються в один батьківський вузол. Однак якщо кілька вузлів мають однакові частоти, стандартна черга в .NET не гарантує стабільного порядку їх вилучення (це залежить від внутрішнього стану бінарної купи). Якщо порядок порушиться, глибини листків можуть вийти різними на різних платформах, що призведе до розбіжності таблиць довжин.

Для забезпечення абсолютної детермінованості вага та порядковий індекс вузла упаковуються в одне 64-бітне число `long`. Вага вузла зміщується на 20 бітів ліворуч, а в молодші 20 бітів записується порядковий індекс вузла. Оскільки в дереві для 256 символів створюється щонайбільше $2 \times 256 - 1 = 511$ вузлів, 20 бітів із запасом вистачає для збереження унікального номера. Черга завжди порівнюватиме спочатку ваги, а при рівності ваг — віддаватиме пріоритет вузлу з меншим індексом.

```csharp
private static long Key(long weight, int index) => (weight << 20) | (uint)index;

```

## 7. Обмеження довжини кодів до 15 біт масштабуванням частот

**Задача.** Забезпечити жорстке дотримання обмеження максимальної глибини дерева (15 біт) за допомогою безпечної евристики масштабування ваг.

**Промпт:**

> Що робити в `HuffmanLengths`, якщо алгоритм побудував дерево з максимальною довжиною коду більше 15 біт? Як зменшити довжину коду за допомогою простого перерахунку частот?
> 
> 

**Відповідь:**

Специфікація формату обмежує довжину будь-якого коду 15 бітами, щоб таблиці розпакування поміщалися в швидку пам'ять і не вимагали 32-бітних регістрів бітового читання. Проте на специфічних розподілах частот (наприклад, експоненційне зростання за числами Фібоначчі) стандартне дерево вироджується в довгий ланцюг глибиною 19–20 рівнів.

Найбільш надійний та алгоритмічно простий підхід полягає в масштабуванні частот (weight scaling). Якщо максимальна глибина листка у збудованому дереві перевищила 15, ми не намагаємося складно перебалансовувати дерево на місці. Замість цього всі ненульові частоти діляться навпіл з додаванням одиниці для захисту від обнулення: `(work[i] + 1) / 2`.

При діленні частоти поступово стискаються в бік 1. Коли всі частоти стають однаковими, дерево стає ідеально збалансованим бінарним деревом з глибиною $\lceil \log_2 256 \rceil = 8$, що гарантовано менше за 15. Таким чином, цикл масштабування завжди успішно завершується за кілька ітерацій і видає валідний набір довжин.

```csharp
while (true)
{
    byte[] lengths = BuildUnlimited(work);

    int maxLength = 0;
    foreach (byte len in lengths)
        if (len > maxLength) maxLength = len;

    if (maxLength <= CanonicalHuffman.MaxCodeLength)
        return lengths;

    for (int i = 0; i < work.Length; i++)
        if (work[i] > 0)
            work[i] = (work[i] + 1) / 2;
}

```

## 8. Підготовка таблиць декодування за збереженими довжинами

**Задача.** Сформувати масиви швидкого доступу для декодера безпосередньо зі збережених 256 байтів довжин без відновлення об'єктів вузлів дерева.

**Промпт:**

> Декодер отримує 256 байтів довжин кодів. Як швидко без побудови об'єктного дерева згрупувати символи в масив `symbols` за зростанням їхніх довжин?
> 
> 

**Відповідь:**

Для розпакування канонічного Гаффмана нам не потрібні структури `Node` з вказівниками `Left` та `Right`. Достатньо знати, які символи відповідають кожній довжині коду, і в якому порядку вони розташовані.

Підготовка виконується за кілька лінійних проходів:

1. Підраховується масив `count`, де індекс — це довжина коду від 1 до 15, а значення — кількість символів, які мають таку довжину.


2. Обчислюється масив префіксних сум `offset`: він визначає стартову позицію в загальному списку символів для кожної довжини.


3. Масив `next` копіює початкові зміщення. Під час фінального проходу по вихідних 256 довжинах кожен символ записується в масив `symbols` за своєю поточною позицією `next[len]++`.



У результаті масив `symbols` містить усі активні байти блоку, ідеально згруповані: спочатку всі символи довжини 1, потім довжини 2, і так далі в алфавітному порядку.

```csharp
var offset = new int[CanonicalHuffman.MaxCodeLength + 2];
for (int len = 1; len <= CanonicalHuffman.MaxCodeLength; len++)
    offset[len + 1] = offset[len] + count[len];

var symbols = new int[TableSize];
var next = (int[])offset.Clone();
for (int s = 0; s < TableSize; s++)
{
    int len = lengths[s];
    if (len != 0)
        symbols[next[len]++] = s;
}

```

## 9. Табличне зчитування окремого символу з потоку

**Задача.** Зрозуміти логіку побітового розпізнавання символу в методі `DecodeSymbol` за допомогою числових меж канонічних префіксів.

**Промпт:**

> Як розпакувати один символ з `BitReader` за допомогою масивів `count` і `symbols`, перебираючи довжину від 1 до 15 біт?
> 
> 

**Відповідь:**

Алгоритм декодування канонічного коду працює без спуску по графу. Він перевіряє гіпотези довжини від $len = 1$ до 15:

На кожній ітерації зчитується один біт і додається до акумулятора `code`. Змінна `first` зберігає найменше значення числового коду для поточної довжини. Якщо зчитаний числовий префікс менший, ніж `first + count[len]`, це означає, що ми знайшли повний валідний код довжини `len`.

Різниця `code - first` показує порядковий номер знайденого символу серед усіх символів цієї довжини. Додаючи його до базового зміщення `index`, ми за одну операцію дістаємо оригінальний байт з масиву `symbols`. Якщо ж поточний префікс виходить за межі `count[len]`, ми переходимо до наступного біта: значення `first` та `code` зсуваються ліворуч, а базовий індекс `index` збільшується на кількість пройдених символів.

```csharp
private static int DecodeSymbol(ref BitReader reader, int[] count, int[] symbols)
{
    int code = 0;
    int first = 0;
    int index = 0;

    for (int len = 1; len <= CanonicalHuffman.MaxCodeLength; len++)
    {
        code |= reader.ReadBit();
        int c = count[len];
        if (code < first + c)
            return symbols[index + (code - first)];

        index += c;
        first = (first + c) << 1;
        code <<= 1;
    }

    throw new ArchiveException(ErrorCode.E_PAYLOAD, "Некоректний код у потоці.");
}

```

## 10. Перевірка префіксності кодів у unit-тестах

**Задача.** Реалізувати структурну перевірку в тестах: підтвердити, що жоден згенерований алгоритмом канонічний код не є префіксом будь-якого іншого коду.

**Промпт:**

> Як у xUnit перевірити властивість префіксності для масиву канонічних кодів Гаффмана, зсуваючи довший код на різницю довжин?
> 
> 

**Відповідь:**

Щоб перевірити префіксність множини бітових послідовностей, необхідно попарно порівняти всі активні символи $a$ та $b$.

Якщо довжини збігаються (`lengths[a] == lengths[b]`), їхні коди повинні просто не дорівнювати один одному.

Якщо ж довжина $a$ строго менша за довжину $b$, код символу $b$ потенційно може починатися з коду $a$. Оскільки ми записуємо біти старшими вперед (MSB-first), префікс довшого коду $b$ знаходиться в його найстарших бітах. Зсунувши значення `codes[b]` праворуч на різницю `lengths[b] - lengths[a]`, ми відкидаємо «хвіст» і залишаємо тільки префікс довжини `lengths[a]`. Якщо цей префікс дорівнює `codes[a]`, властивість префіксності порушена, і однозначне декодування стає неможливим.

```csharp
if (lengths[a] == lengths[b])
{
    Assert.NotEqual(codes[a], codes[b]);
}
else
{
    // Відкидаємо молодші біти і порівнюємо префікс
    Assert.NotEqual(codes[a], codes[b] >> (lengths[b] - lengths[a]));
}

```

## 11. Стрес-тест на експоненційних частотах Фібоначчі

**Задача.** Створити синтетичний тестовий набір даних, який провокує формування дерева з максимальною глибиною, щоб перевірити роботу механізму обмеження в 15 біт.

**Промпт:**

> Як створити тестовий масив частот за числами Фібоначчі для перших 20 символів, щоб перевірити спрацювання ліміту довжини коду 15 біт та коректність відновлення даних?
> 
> 

**Відповідь:**

Дерево Гаффмана будується шляхом об'єднання двох найменших вузлів. Якщо частоти символів зростають як послідовність Фібоначчі ($F_n = F_{n-1} + F_{n-2}$), кожна нова сума двох менших елементів виявляється рівною наступному елементу ряду. Через це дерево не розгалужується рівномірно, а перетворюється на вироджений однобічний бамбук, де глибина кожного наступного листка на 1 більша за попередній. Для 20 символів глибина сягає 19 рівнів.

У цьому тесті ми формуємо масив із такими частотами і генеруємо тестові дані з відповідною кількістю повторень кожного байта. Тест перевіряє дві речі:

1. Метод `HuffmanLengths.Build` помітив перевищення ліміту і скоригував масив так, що `lengths.Max() <= 15`.


2. Після застосування скоригованих довжин повний цикл кодування та декодування (`AssertRoundTrip`) повертає вихідний масив байтів без спотворень.



```csharp
var freq = new long[256];
long a = 1, b = 1;
for (int i = 0; i < 20; i++)
{
    freq[i] = a;
    (a, b) = (b, a + b);
}

byte[] lengths = HuffmanLengths.Build(freq);
Assert.True(lengths.Max() <= CanonicalHuffman.MaxCodeLength);

var data = new List<byte>();
a = 1; b = 1;
for (int i = 0; i < 20; i++)
{
    for (long k = 0; k < a; k++) data.Add((byte)i);
    (a, b) = (b, a + b);
}
AssertRoundTrip(data.ToArray());

```

## 12. Мутаційне тестування інверсією бітів

**Задача.** Переконатися, що декодер захищений від аварійних падінь платформи при отриманні пошкоджених файлів і завжди викидає лише очікуваний доменний виняток `ArchiveException`.

**Промпт:**

> Як написати цикл для тесту, який по черзі інвертує біти в кожному байті валідного архіву масками `0x01`, `0x80`, `0xFF` і очікує лише `ArchiveException`?
> 
> 

**Відповідь:**

Однією з головних вимог надійності до архіватора є безпека при читанні пошкоджених архівів. Навіть якщо біти стисненого потоку пошкоджені, внутрішні методи декодера не повинні призводити до аварійних системних збоїв на кшталт `IndexOutOfRangeException` (вихід за межі буфера) чи `NullReferenceException`.

Мутаційний тест бере повністю валідний закодований блок і послідовно проходить по кожному його байту. Для кожного байта застосовуються три типи спотворень: інверсія молодшого біта (`0x01`), інверсія старшого біта (`0x80`) та повна інверсія байта (`0xFF`). Отриманий масив передається в `Decode` всередині блоку `try / catch (ArchiveException)`.

Якщо метод успішно декодує дані або коректно відхилить їх через контрольований `ArchiveException`, ітерація вважається успішною. Якщо ж вилетить будь-який інший виняток середовища виконання, `catch` його пропустить, і тест автоматично завалиться, вказавши на місце вразливості.

```csharp
foreach (int index in Enumerable.Range(0, original.Length))
{
    foreach (byte mask in new byte[] { 0x01, 0x80, 0xFF })
    {
        byte[] mutated = (byte[])original.Clone();
        mutated[index] ^= mask;

        try
        {
            HuffmanCodec.Decode(mutated, data.Length);
        }
        catch (ArchiveException)
        {
            // Очікувана контрольована відмова
        }
    }
}

```
