# Рішення: Інтеграція (hrabovskaol-ai), Чекпоінт 1

Формат: проблема → варіанти → рішення → чому.

## 1. Розкладка 41-байтового заголовка тому

**Проблема.** У методичці сказано лише, що відкритий заголовок має 41 байт і містить magic, версію, номер/кількість томів, salt, nonce, ciphertext_len. Точні розміри й порядок полів у FORMAT_SPEC_P2.md.

**Варіанти.** (а) чекати специфікацію; (б) вивести розкладку з суми розмірів і зробити її змінюваною в одному місці.

**Рішення.** (б): `magic(4) "SARC" | версія(1) | номер тому(2) | кількість томів(2) | salt(16) | nonce(12) | ciphertext_len(4)`, усе big-endian, номер тому з 1.

**Чому.** 4+1+2+2+16+12+4 = 41, тобто сума збігається, а salt(16) і nonce(12) задані методичкою. Порядок полів, ширина полів номера/кількості томів і нумерація з 1 це припущення. **Потрібно звірити з FORMAT_SPEC_P2.md до merge.** Усе зосереджено в `FormatConstants.cs` і `VolumeHeader.cs`, а `VolumeHeaderTests.Write_ProducesExactBytes` фіксує байти.

## 2. Службовий заголовок блока: 15 байт

**Проблема.** Вага блока в рюкзаку = `coded_len + 15`, але звідки 15, методичка не пояснює.

**Варіанти.** (а) довільні 15 байт; (б) мінімальний набір полів, який дає саме 15.

**Рішення.** (б): `file_index(2) | block_index(4) | raw_len(4) | coded_len(4) | стратегія(1)` = 15.

**Чому.** Блоки мають бути самоописними: при пакуванні в томи вони підуть не по порядку, тож треба знати файл і номер блока. `coded_len` окремо від `raw_len` потрібен для стиснення. Стратегія на рівні блока залишає місце для адаптивної стратегії всередині файлу (експертний рівень Blackcat-404). Те саме потрібно звірити зі специфікацією.

## 3. Помилки: ArchiveException з кодом

**Проблема.** Для bad\_\*.arc потрібні коди E_MAGIC, E_LENGTH, E_HMAC, E_PAYLOAD, E_CODE, E_CRC. У CP3 вони мають замінити винятки.

**Варіанти.** (а) Result-тип одразу; (б) один виняток з полем `Code`.

**Рішення.** (б): `ArchiveException(ErrorCode, message)`. Версія формату, що не збігається, дає E_MAGIC (окремого коду для неї в списку немає).

**Чому.** Усередині парсера виняток простіший, ніж протягувати Result крізь кожен виклик. Верхній рівень (CLI, CP3) перетворить його на код. Тести перевіряють, що на будь-якому зіпсованому вході вилітає лише `ArchiveException`, а не `IndexOutOfRange` чи `OutOfMemory`.

## 4. Власний CRC32

**Проблема.** CRC32 потрібен для кожного файлу. У .NET він є лише в окремому NuGet-пакеті.

**Рішення.** Власна табличка (поліном 0xEDB88320), тест на вектор `"123456789" → 0xCBF43926`.

**Чому.** Це 20 рядків, а додаткових залежностей у тракті методичка не любить (зовнішні бібліотеки дозволені лише для AES, SHA-256, файлів, графіків і тестування).

## 5. Безпечні імена

**Проблема.** Path traversal при розпакуванні.

**Рішення.** Імена перевіряються і при записі, і при читанні (`SafeNames`). Відхиляються: порожнє, `/ \ :` NUL, імена лише з крапок (`.`, `..`, `...`), понад 255 байт UTF-8, некоректний Unicode. Дублікати імен в одному архіві теж відхиляються. Код помилки E_PAYLOAD, як у методичці.

**Чому.** Заборона роздільників вже виключає шляхи, а «лише крапки» додатково закриває `...`, яке Windows спрощує до порожнього імені. Перевірка саме на читанні важлива, бо архів може бути чужим або підробленим.

## 6. CI

**Проблема.** Кожна зміна має перевірятися автоматично.

**Рішення.** GitHub Actions: збірка й тести на кожен PR і пуш у main, матриця ubuntu + windows, кеш NuGet, скасування застарілих прогонів, TRX і coverage як артефакти. Потрібно вручну (Settings → Branches → main): увімкнути **Require status checks** і додати обидві перевірки `build & test (...)`.

**Чому.** Команда може працювати на різних ОС (шляхи, роздільники рядків), тож один Linux-прогін це пропустив би. Без обов'язкових перевірок у гілці main «CI на кожен PR» лише декоративний.

# Рішення: База даних (Blackcat-404), Чекпоінт 1

## 7. СУБД і спосіб доступу до неї

**Проблема.** Уже на CP1 базове Q треба записати в БД, а на CP2–CP3 туди підуть експерименти, журнал ГА, прогони навчання класифікатора й історія архівацій, і з неї будуватимуться 5 таблиць звіту. Схема ростиме з кожним чекпоінтом, а на CP2 шар доступу має дати параметризовані запити, транзакції й обмеження цілісності.

**Варіанти.** СУБД: (а) SQLite, файл поруч із програмою, нічого не треба встановлювати; (б) PostgreSQL; (в) MS SQL Server. Доступ: (г) ADO.NET і SQL вручну; (ґ) EF Core з міграціями.

**Рішення.** (в) + (ґ): MS SQL Server через EF Core, схема задається кодом (`src/SmartArchiver.Data`). Програма сама застосовує міграції при першому зверненні до БД (`Database.Migrate()`), окремих SQL-скриптів немає. На CP1 у схемі дві таблиці: `MeasurementRuns` (прогін вимірювання Q з полями журналу прогону: дата, коміт, seed, параметри, набір даних, результат, час) і `MeasurementFileResults` (результат по кожному файлу). Решта таблиць додаватиметься новими міграціями.

**Чому.** Міграції EF Core дають версіоновану схему: кожна зміна є окремим файлом у git, а в кожного учасника база оновлюється сама. Вимоги CP2 закриваються штатно: запити EF Core параметризовані, один `SaveChanges` виконується однією транзакцією, ключі, NOT NULL і CHECK описуються в моделі. SQL Server має повноцінні транзакції й обмеження та зручні інструменти, щоб показати дані на захисті, а в Docker він однаково запускається на Windows, Linux і macOS. Мінус у тому, що потрібен запущений сервер, на відміну від SQLite. Це закриває рішення 8. Обмеження методички на зовнішні бібліотеки стосуються тракту архівації. БД живе поруч із ним і не торкається ні формату архіву, ні самого стиснення. Якщо від SQL Server доведеться відмовитися, EF Core підтримує й SQLite: зміниться провайдер і міграції, а не код, що пише результати.

## 8. БД необов'язкова, і кожен налаштовує свою

**Проблема.** У кожного учасника свій SQL Server зі своїм паролем, а рядок підключення з паролем не можна комітити. Проєкт має запускатися з README без втручання автора (E3). Тести й CI не повинні падати там, де сервера немає (Windows-раннер GitHub не запускає Linux-контейнери).

**Варіанти.** (а) один спільний рядок підключення в `appsettings.json` у git; (б) рядок у змінній середовища; (в) `appsettings.json` у git з порожнім рядком плюс особистий `appsettings.Local.json` поруч, доданий у `.gitignore`.

**Рішення.** (в). Порожній рядок означає, що БД вимкнена: сховище приймає виклики й нічого не пише. До сервера звертаються лише ті команди, яким потрібна БД (зараз це `db`), тож `pack`, `unpack`, `info` і `demo` працюють і без SQL Server. Рядок без `Database=` відхиляється, інакше таблиці потрапили б у `master`. Помилки БД перетворюються на `DatabaseException`, у повідомленні якої є сервер і назва бази, але немає пароля, а CLI повертає код 4. Тести, яким потрібен сервер, позначені `[DatabaseFact]`: вони виконуються лише тоді, коли задано змінну `SMARTARCHIVER_TEST_SQLSERVER`, і кожен працює у власній тимчасовій базі, яку видаляє після себе. У CI Linux-задача піднімає SQL Server у контейнері з паролем, згенерованим на кожен прогін, а Windows-задача ці тести пропускає.

**Чому.** Пароль не потрапляє в git, і кожен підключається до свого сервера, нічого не змінюючи в спільних файлах. Файл поруч із програмою простіший за змінну середовища: однаково працює на всіх ОС і при запуску з IDE, і його видно. Архіватор, який перевіряють кейси C1 і запуск з README, не залежить від того, чи піднятий SQL Server. Окрема база на кожен тест означає, що тести не залежать від даних один одного і не псують робочу базу.

# Рішення: Стиснення (keytrw), Чекпоінт 1

## 9. Формат таблиці довжин кодів у блоці

**Проблема.** Декодер Гаффмана відновлює коди з довжин, записаних у блок. Точний байтовий формат таблиці задає FORMAT_SPEC_P2.md, якого команді не надали.

**Варіанти.** (а) таблиця фіксованого розміру 256 байт, індекс = символ, 0 означає «не використовується»; (б) розріджена таблиця: бітова карта використаних символів (32 байти) + довжини лише для них; (в) довжини кодуються окремим Гаффманом поверх довжин, як у DEFLATE.

**Рішення.** (а): `lengths[256]`, `lengths[s]` — довжина коду символу `s`.

**Чому.** Найпростіша реалізація для CP1, де алфавіт — усі байти 0…255, декодеру нічого зіставляти. Варіанти (б) і (в) ефективніші за розміром, але не потрібні для першого чекпоінту. **Потрібно звірити з FORMAT_SPEC_P2.md до merge**, особливо якщо специфікація вимагає окремих алфавітів LIT/LEN/DIST (методичка, 10.22) — тоді формат міняється на CP2. `TableSize` винесено як константу саме для цього переходу. Усе зосереджено в `HuffmanCodec.cs` і `HuffmanLengths.cs`.

## 10. Порядок бітів у закодованому потоці

**Проблема.** Без FORMAT_SPEC_P2.md невідомо, старший чи молодший біт коду йде першим, і чим доповнюється останній неповний байт.

**Варіанти.** (а) старший біт першим (MSB-first), доповнення нулями; (б) молодший біт першим (LSB-first), як у DEFLATE.

**Рішення.** (а).

**Чому.** Найпоширеніший порядок для навчальних реалізацій і узгоджується з прикладом з методички (6.5). Позначено як припущення в `BitIo.cs`; якщо специфікація вимагає іншого порядку, міняється лише цей файл, решта кодека від напрямку бітів не залежить.

## 11. Порожній вхід у HuffmanCodec.Encode

**Проблема.** Порожня таблиця довжин не проходить перевірку рівності Крафта (`CanonicalHuffman.AssignCodes`), тож порожній блок закодувати напряму не можна.

**Варіанти.** (а) `Encode` кидає `ArgumentException`: виклик з порожнім блоком — помилка виклику, Writer не створює блоків для порожніх файлів; (б) `Encode` повертає порожній результат, `Decode` з `rawLength = 0` повертає порожній масив.

**Рішення.** (а).

**Чому.** Узгоджується з тим, як уже працює `ArchiveWriter`: порожній файл не має жодного блока (`offset = 0`, блоків 0). Кодек на порожньому вході в реальному архіві ніколи не повинен викликатися, тож така ситуація — помилка виклику (`ArgumentException`), а не пошкоджені дані архіву (`ArchiveException`).

## 12. Видимість internal-класів кодека для тестів

**Проблема.** `CanonicalHuffman`, `HuffmanLengths`, `HuffmanCodec`, `BitWriter`, `BitReader` — деталі реалізації, не частина публічного API `SmartArchiver.Core`, але тестам (`SmartArchiver.Core.Tests`) потрібен прямий доступ до них.

**Варіанти.** (а) зробити класи `public`; (б) лишити `internal`, дати доступ тестовій збірці через `InternalsVisibleTo`.

**Рішення.** (б): `InternalsVisibleTo` на `SmartArchiver.Core.Tests` у `SmartArchiver.Core.csproj`.

**Чому.** API `SmartArchiver.Core` лишається мінімальним: зовнішній код працює лише через `ArchiveWriter`/`ArchiveReader`, не залежить від внутрішньої структури кодека, яку доведеться переробити на CP2 під алфавіти LIT/LEN/DIST.

## 13. Тести, відкладені через структуру поточного формату таблиці

**Проблема.** Методичка (6.5, п'ята перевірка) вимагає тестів на довжину коду 0 для використаного символу, дубльований символ і символ поза алфавітом. У поточному форматі (таблиця з 256 записів, індекс = символ) усі три ситуації структурно неможливі.

**Рішення.** Тести не написано на CP1.

**Чому.** Тестувати неможливу в поточному коді ситуацію означало б тестувати вигадану поведінку. Повернутися до цього пункту, якщо формат стане розрідженим (п. 9, варіант б) або з'являться окремі алфавіти LIT/LEN/DIST на CP2.

# Рішення: Архітектура (Blackcat-404), після Чекпоінту 1

## 14. Проєкт на кожну зону

**Проблема.** Усі зони лежали в одному проєкті Core, а їхні тести — в одному Core.Tests. 13.10 файл однієї зони (`ArchiveSecurity.cs`) не потрапив у коміт, і збірка та тести впали в усіх. Межі між зонами трималися лише на домовленості. Окремо порожній `Cp1integration` з Docker-профілем Visual Studio вимагав WSL, а другий файл рішення `SmartArchiver.sln` без проєктів Data ламав відновлення пакетів і `dotnet build` з кореня.

**Варіанти.** (а) одна бібліотека з теками на зони; (б) окремий проєкт на кожну зону; (в) як (б), але формат окремо від тракту архіву.

**Рішення.** (б): Core (спільні типи), Compression, Security, Archive (формат і тракт), Data, Cli, App, і окремий тестовий проєкт на кожен. Compression залежить лише від Core, Security ні від кого, Archive — від Core і Security, CLI — від Archive і Data. Код перенесено через `git mv`, змінено лише namespace. `ArchiveSecurity` розділено: криптографічні примітиви лишилися в Security, а склейка з форматом томів (`Protect`, `Unprotect`, `BuildProtected`, `ReadProtected`) без змін перейшла в Archive як `ProtectedArchive`, інакше Security залежав би від формату. `Cp1integration` і `SmartArchiver.sln` видалено.

**Чому.** Межі зон збігаються з межами проєктів: видно, чия це робота, а компілятор не дає одній зоні залізти в нутрощі іншої. Поломка в зоні зачіпає лише її тести й тракт. У проєктах Compression і Security немає сторонніх пакетів, тож видно, що Гаффман і решта алгоритмів написані самостійно. (в) відкинуто: формат і тракт належать одній зоні й тісно пов'язані, а розділити їх можна пізніше.

## 15. Спільні налаштування збірки, центральні версії пакетів, лінтер

**Проблема.** Налаштування повторювалися в кожному `.csproj`, версії пакетів додавалися вручну і розходилися, EF Core тягнув `System.Security.Cryptography.Pkcs` 9.0.11 з відомими вразливостями (GHSA-846f-f764-76mx, GHSA-2fmv-rv2c-59x7), лінтера не було (критерій C4), а різні SDK та IDE давали різні, незрозумілі помилки.

**Варіанти.** (а) лишити налаштування в кожному проєкті; (б) винести їх у спільні файли й увімкнути лінтер.

**Рішення.** (б): `Directory.Build.props` (платформа, nullable, аналізатори .NET `latest-recommended` і правила стилю), `Directory.Packages.props` (усі версії пакетів, Pkcs закріплено на 10.0.13), `global.json` (SDK 10), `.editorconfig` (стиль і кодування), `tests/Directory.Build.props` (пакети тестів). У CI збірка йде з `-warnaserror`, локально попередження лишаються попередженнями. CA1707 вимкнено для `ErrorCode` (імена `E_*` задає методичка) і для імен тестів.

**Чому.** `.csproj` містять лише свої відмінності, нову версію пакета міняють в одному місці, і в усіх збирається те саме. Старий SDK одразу каже, що потрібен .NET 10. Лінтер, який не ламає CI, швидко перестають помічати, тож у CI попередження стають помилками.

## 16. Параметри захисту і розкладка захищеного тому

**Проблема.** Архів має бути зашифрований і автентифікований, але `FORMAT_SPEC_P2.md` команді не надали.

**Рішення.**
- PBKDF2-HMAC-SHA256: 100 000 ітерацій, 16-байтна випадкова сіль, 64 байти результату (32 для AES, 32 для HMAC).
- AES-256-CTR: 12-байтовий випадковий nonce, далі 32-бітний big-endian лічильник від 0.
- HMAC-SHA256: 32-байтовий тег від `header(41) || ciphertext`; перевіряється до розшифрування порівнянням за сталий час.
- Розкладка: `41-byte header | ciphertext | 32-byte HMAC`.
- Помилка перевірки автентичності — `E_HMAC`. Паролі й ключі в БД не записуються.

**Звірка.** Сумісність з еталонними архівами не підтверджена: розкладку й лічильник CTR потрібно звірити з `FORMAT_SPEC_P2.md`, коли він з'явиться.

# Рішення: Аналіз файлу (Blackcat-404), Чекпоінт 1

## 17. Точні визначення ознак файлу

**Проблема.** Методичка називає ознаки (ентропія, гістограма, частка друкованих символів, довжина рядків, автокореляція на лагах 1–16, ентропія біграм), але не визначає їх точно. Від визначень залежить, що бачитиме класифікатор, і що відповідати на захисті.

**Варіанти.** Друковані символи: лише `0x20…0x7E` чи разом з табуляцією й переходами рядка. Довжина рядка: рахувати `\r` чи ні. Автокореляція: сира коваріація чи нормована вибіркова автокореляція. Обсяг: увесь файл чи його частина.

**Рішення.**
- Ентропія: `H = −Σ p·log2 p` по 256 значеннях байта, від 0 до 8 біт.
- Гістограма: частота кожного значення байта, сума 1.
- Друковані: `0x20…0x7E`, `\t`, `\n`, `\r`; частка від усіх байтів.
- Середня довжина рядка: кількість символів без `\n` і `\r`, поділена на кількість рядків (останній рядок без `\n` теж рахується).
- Автокореляція: `r(k) = Σ(x[i]−m)(x[i+k]−m) / Σ(x[i]−m)²` для `k = 1…16`, від −1 до 1; для сталих даних або лагу, не меншого за довжину, `0`.
- Ентропія біграм: та сама формула по парах сусідніх байтів, від 0 до 16 біт.
- Ознаки рахуються по всьому файлу в пам'яті; потокове читання великих файлів — на CP2 разом із класифікатором.

**Чому.** Нормовані величини мають сталі межі, тож їх зручно подавати на вхід перцептрона. `\t`, `\n`, `\r` є в будь-якому тексті, а `\r` не враховується, щоб той самий текст з Windows і з Linux мав однакову довжину рядків. Кирилиця в UTF-8 займає два не-ASCII байти, тому в українському тексті частка друкованих ASCII близько 40%; це свідомо: ознака описує саме ASCII, а відрізнити такий текст від бінарних даних допомагають ентропія й автокореляція. Тести перевіряють ознаки на відомих даних (нулі, шум, текст), як радить методичка (10.41).

## 18. Будова перцептрона

**Проблема.** Потрібен власний багатошаровий перцептрон з навчанням і збереженням ваг (готові бібліотеки заборонені). На CP2 він класифікуватиме файли на 7 типів (`file_type` 0…6 з `FORMAT_SPEC_P2`).

**Варіанти.** Активація прихованих шарів: sigmoid, tanh, ReLU. Вихід: sigmoid з квадратичною помилкою чи softmax з cross-entropy. Збереження ваг: власний двійковий формат чи JSON.

**Рішення.** Довільна кількість шарів, у прихованих `tanh`, на виході `softmax`, помилка cross-entropy, навчання стохастичним градієнтним спуском із зворотним поширенням після кожного прикладу. Початкові ваги — рівномірні в межах `±√(6/(n_in+n_out))` з генератора із заданим seed, зсуви нульові. Ваги зберігаються в JSON через `System.Text.Json`. Правильність зворотного поширення перевіряється чисельним градієнтом, навчання — на XOR.

**Чому.** Softmax із cross-entropy природні для кількох класів і дають простий градієнт на виході `p − onehot(клас)`. `tanh` центрований навколо нуля і на маленьких мережах не має «мертвих» нейронів, як ReLU. Seed робить кожен запуск відтворюваним, а методичка вимагає порівнювати кілька ініціалізацій. JSON читається людиною, а `System.Text.Json` входить до .NET, тож сторонньої бібліотеки немає. Швидкість навчання для XOR виміряна: з `0.1` і 4 прихованими нейронами вчаться всі 30 перевірених seed, з `0.5` застрягає близько половини, тому тест використовує `0.1` і кілька seed.

# Рішення: База даних (Blackcat-404), Чекпоінт 2

## 19. Таблиці експериментів і обмеження цілісності

**Проблема.** На CP2 усі результати експериментів пишуться в БД: розбір потоку (жадібний, лінивий і ДП-розбір LZ77), пакування томів (ДП-рюкзак проти жадібного) і навчання класифікатора. Потрібна схема, з якої потім будуватимуться таблиці звіту, і шар доступу з параметризованими запитами, транзакціями та обмеженнями цілісності.

**Варіанти.** (а) одна таблиця з колонкою JSON для будь-яких результатів; (б) окрема таблиця з усіма полями журналу прогону для кожного експерименту; (в) спільна таблиця `Experiments` з полями журналу прогону і окремі типізовані таблиці результатів.

**Рішення.** (в). `Experiments` зберігає вид експерименту, дату, коміт, seed, набір даних і параметри. `ParsingResults`, `PackingResults` і `TrainingRuns` посилаються на неї зовнішнім ключем із каскадним видаленням. Види й методи зберігаються текстом (`Parsing`, `Greedy`, `Dp`…), а CHECK з переліком дозволених значень будується з самих C#-переліків. Обмеження CHECK додано і до нових, і до наявних таблиць: група 0–6 (`file_type` з `FORMAT_SPEC_P2`), розміри й час не від'ємні, `t_ref > 0`, використано не більше за місткість тому, macro-F1 від 0 до 1, епохи й швидкість навчання додатні, набір даних не порожній. Сховище отримало `SaveExperiment`, `GetExperiment` і `ListExperiments`.

**Чому.** JSON (а) не дає ні типів, ні CHECK, і з нього незручно будувати звіт. Окремі таблиці (б) повторювали б поля журналу прогону тричі. Спільна таблиця дає один журнал прогонів, а типізовані результати можна перевіряти базою. Обмеження в самій базі відхиляють неможливі значення навіть у разі помилки в коді, що пише результати. EF Core передає всі значення параметрами, тож текст на кшталт `x'; DROP TABLE Experiments; --` зберігається як звичайний рядок; це перевіряє тест. Експеримент разом з усіма результатами записується одним `SaveChanges`, тобто однією транзакцією: тест перевіряє, що експеримент, у якому один результат порушує CHECK, не зберігається зовсім.

Рішення: Стиснення (Артем), Чекпоінт 2
20. Жадібний розбір LZ77
Проблема. Для стиснення потрібен розбір потоку на літерали та посилання на повторювані фрагменти, але повний перебір вікна пошуку занадто повільний.

Варіанти. (а) порівнювати кожну позицію з усім попереднім вікном; (б) шукати кандидатів через хеш-ланцюжки.

Рішення. (б): MatchFinder шукає збіги в межах вікна LZ77, а GreedyParser обирає найдовший серед перевірених кандидатів. Глибину обходу ланцюжка обмежено параметром maxChain (типово 256).

Чому. Обмеження обходу дає передбачуваний час роботи. Це практична жадібна евристика, але не гарантія пошуку найдовшого збігу серед абсолютно всіх позицій вікна. Розбір перевірено unit-тестами та відновленням вихідних байтів.
21. Лінивий жадібний розбір LZ77
Проблема. Жадібний парсер інколи бере збіг зараз, хоча з наступного байта починається суттєво довший збіг.

Варіанти. (а) завжди брати поточний збіг; (б) порівнювати поточний збіг із наступним.

Рішення. (б): LazyParser відкладає поточне посилання та записує літерал, якщо збіг на наступній позиції довший щонайменше на minLazyGain (типово 2 байти). Для пошуку використовується той самий MatchFinder.

Чому. Невеликий перегляд уперед може поліпшити стиснення без повного оптимального пошуку. Тести перевіряють і відкладання збігу, і коректне відновлення даних.
22. Вимірювання Greedy і Lazy на групах корпусу
Проблема. Треба порівняти час та фактичний розмір стиснення за групами file_type 0–6 і підготувати результати до збереження в БД, не прив'язуючи алгоритми до SQL Server.

Варіанти. (а) вимірювати лише кількість токенів; (б) кодувати результат Huffman і вимірювати байти; (в) додати залежність від БД до Compression.

Рішення. Використано (б): Lz77ParsingBenchmark вимірює час і розмір після LZ77 + Huffman. ParsingComparisonRunner агрегує результати по групах із Datasets/0…Datasets/6. Збереження через Experiment і ParsingResult виконується на рівні CLI через IMeasurementStore.SaveExperiment(); бібліотека Compression не залежить від Data.

Чому. Кількість токенів не дорівнює реальному обсягу стиснутого блока. На вже стиснутих даних результат може бути більшим за оригінал через таблиці й службові дані — це не помилка експерименту. Порівняння всіх семи груп виконано; фактичний запис у SQL Server ще потрібно перевірити окремо.
23. Об'єднання LZ77 і трьох таблиць Huffman
Проблема. Токени LZ77 самі по собі ще не є готовим стиснутим блоком. Формат CP2 вимагає окремі алфавіти для літералів, довжин і відстаней.

Варіанти. (а) одна таблиця для всіх значень; (б) три канонічні таблиці LIT, LEN, DIST.

Рішення. (б): Lz77BlockEncoder рахує частоти, будує окремі канонічні коди, записує таблиці та бітовий потік токенів. Lz77BlockDecoder відновлює блок; для відсутніх у потоці довжин або відстаней таблиця залишається структурно коректною.

Чому. Це відповідає специфікації формату, а три алфавіти мають різні розподіли частот. Тести пройшли для Greedy/Lazy, випадкових даних і довгих повторень; перевірялося побайтове відновлення.
24. ДП-розбір із фіксованими вартостями
Проблема. Найдовший локальний збіг не завжди дає найменшу загальну вартість послідовності токенів.

Варіанти. (а) залишити локальний жадібний вибір; (б) динамічне програмування за вартістю суфікса.

Рішення. (б): DpParser мінімізує суму вартостей, де літерал коштує 9 біт, а посилання — 17 + max(0, bit_length(dist − 1) − 1) біт. Збіги шукаються з обмеженням кількості кандидатів; оптимум визначається в межах розглянутих варіантів.

Чому. DP враховує наслідки вибору токена для всього залишку блока. Тести перевірили відновлення та Cost(DP) ≤ Cost(Greedy) на вибраних наборах. Ця нерівність стосується модельної вартості, а не обов'язково розміру фактичного Huffman-блока.
25. ДП-розбиття на блоки з власними таблицями Huffman
Проблема. Фіксовані межі блоків не враховують, що на різних ділянках даних Huffman-таблиці й ступінь стиснення можуть відрізнятися.

Варіанти. (а) завжди ділити по 64 КіБ; (б) вибирати межі динамічним програмуванням за сумарним розміром блоків.

Рішення. (б): DpBlockSplitter обчислює F[j] = min(F[i] + T(i,j) + H(i,j)), використовуючи фактичний результат Lz77BlockEncoder для кожного кандидата та враховуючи 15 байтів службового запису блока. Кандидатні межі беруться із сітки (типово 16 КіБ); фіксовані межі 64 КіБ також доступні.

Чому. Кожний блок отримує власні таблиці Huffman; включення фіксованого розбиття до множини кандидатів забезпечує Size(DP) ≤ Size(Fixed) за однакового способу підрахунку. Гарантія діє для допустимих меж сітки, а не для всіх позицій байтів. Unit-тести пройшли; наскрізне підключення до ArchiveWriter/ArchiveReader виконує учасник 4.

Межа інтеграції. Для передачі учаснику 4 підготовлено Lz77CompressionService з методами PrepareFixedBlocks(), PrepareDpBlocks() і DecodeBlock(). Його тести пройшли. Бібліотека Compression не повинна залежати від CLI чи Data; підключення до реального архіву та повний round-trip .arc перевіряються окремо.
# Рішення: Аналіз файлу (Blackcat-404), Чекпоінт 2

## 26. Навчання класифікатора типу файлу

**Проблема.** Класифікатор має визначати `file_type` 0…6 за ознаками файлу, навчатися на `train/`, а модель має обиратися за macro-F1 на `valid/` щонайменше з трьох ініціалізацій. Справжніх `train/` і `valid/` від викладача ще немає, є лише командний `Datasets/` (`keytrw`): 3–4 файли на групу.

**Варіанти.** Приклад: цілий файл чи шматок файлу. Поділ train/valid: випадково по шматках чи по файлах. Вхід мережі: усі 256 значень гістограми чи стиснений набір ознак.

**Рішення.**
- Приклад — шматок файлу по 4096 байтів (не більше 24 з одного файлу, хвіст коротший за пів шматка відкидається; файл, не довший за шматок, — один приклад).
- Поділ за файлами: кожен третій файл групи (за іменем) іде у valid, решта в train. Шматки одного файлу ніколи не потрапляють в обидва набори.
- Вхід — 38 чисел у межах 0…1 (автокореляція −1…1): ентропія /8, ентропія біграм /16, частка друкованих ASCII, логарифм довжини рядка (стеля 1000), частки байтів `0x00` і `0xFF`, гістограма, згрупована в 16 інтервалів, автокореляція на лагах 1–16.
- Мережа `38-16-7`, 100 епох, швидкість навчання 0.05, приклади перемішуються на кожній епосі; seed 1–5, обирається найкращий macro-F1 на valid. macro-F1 — середнє F1 по класах, що трапилися серед справжніх або передбачених міток.
- Команда `smartarchiver train-classifier [датасет] [модель.json]` друкує таблицю запусків і матрицю помилок, зберігає модель і пише прогони в `TrainingRuns`. Навчена модель лежить у `src/SmartArchiver.Analysis/Model/classifier.json` і вбудована в збірку.

**Результат на `Datasets/`.** train macro-F1 1.000, valid 0.714 для всіх п'яти seed і всіх перевірених налаштувань (8/16/32 нейрони, швидкість 0.01/0.05, 100/300 епох, шматки 2/4 КБ). У матриці помилок valid п'ять груп вгадані повністю, а дві плутаються між собою: `sample.py` (код) розпізнано як структуровані дані, `table.csv` (структуровані) — як код. У train код — лише C# і C++, структуровані — лише JSON і XML, тож Python і CSV для мережі нові «підвиди». Спроба додати частки класів символів (цифри, літери, дужки, розділювачі, лапки) нічого не змінила, тому ці ознаки не додано.

**Чому.** Шматки дають достатньо прикладів із кількох файлів, а поділ за файлами не дає valid «підглянути» train: інакше valid показував би майже 1.0 без реальної здатності узагальнювати. 38 стиснених ознак замість 256 значень гістограми зменшують перенавчання на малому наборі. Обмеження набору (два файли на групу для навчання) пояснює валідаційний результат; механізм готовий до `train/` (350) і `valid/` (105) від викладача — достатньо вказати їх замість `Datasets/`.

## 27. Контракт `IFileAnalyzer` і вибір стратегії стиснення

**Проблема.** Архів має отримувати від аналізу тип файлу й стратегію. Нумерація `FileKind` (`Unknown=0, Text=1…7`) і `CompressionStrategy` (`NoCompression=0, Huffman=1, Lz77Huffman=2`) не збігалася з `FORMAT_SPEC_P2`: `file_type` — 0…6, а в контрольному архіві `ref_01` файл, стиснений LZ77 і Гаффманом, має `strategy = 1`; окремого «лише Гаффмана» специфікація не має.

**Варіанти.** Нумерація: залишити свою й перекладати при записі чи взяти нумерацію специфікації. Стратегія: лише за класом, лише за ентропією чи за обома.

**Рішення.**
- `FileKind`: `Text=0, SourceCode=1, Structured=2, Raster=3, Executable=4, AlreadyCompressed=5, Artificial=6` — як `file_type`. `Unknown=255` лишився для «ще не класифіковано»: він поза діапазоном специфікації, тож в архів записатися не може.
- `CompressionStrategy`: `NoCompression=0, Lz77Huffman=1`.
- Контракт у Core: `IFileAnalyzer.Analyze(байти)` → `FileAnalysis(Kind, Confidence, Strategy)`. Реалізація — `FileAnalyzer` в Analysis з вбудованою моделлю.
- Стратегія: порожній файл або ентропія ≥ 7.9 біта (шум, стиснені дані) — без стиснення; клас «вже стиснуте» **і** ентропія ≥ 7.0 — без стиснення; решта — LZ77 + Гаффман.

**Чому.** Однакова з форматом нумерація знімає перекладання й помилки в ньому. Помилки стратегії несиметричні: стиснути вже стиснене коштує лише часу (кодер однаково збереже блок як є, якщо виграшу немає), а не стиснути текст — усього виграшу в розмірі. Тому «не стискати» лише тоді, коли класифікатор і дані згодні. Без цієї умови вбудована модель лишала б нестисненим український `README.md`, бо приймає його за «вже стиснуте» (88%). Сама ентропія не вирішує: растр `gradient.bmp` має 7.75 біта і добре стискається, тож поріг шуму стоїть нижче за стиснені дані (7.99), а головне рішення ухвалює класифікатор (методичка, 10.28).

## 28. Передбачення наступного байта (просунутий рівень)

**Проблема.** За умовою мережа за k попередніми байтами передбачає наступний, кодується залишок `(справжній − передбачений) mod 256`, і таблицею треба показати, де це знижує ентропію, а де ні. Розпакування мусить повторити прогноз побайтово: «ваги записуються в архів або мережа детермінована». Формат режиму `PREDICTION` специфікація не визначає (розділ 2.5, командне розширення).

**Варіанти.** Ваги: окремо для кожного файлу в архіві чи одна детермінована модель. Активація прихованого шару: tanh чи softsign. Контекст: 2, 3 або 4 байти; розмір мережі й обсяг навчання.

**Рішення.**
- `BytePredictor`: вхід — k = 2 попередні байти як one-hot (512 входів), прихований шар 32 нейрони, 256 виходів; прогноз — вихід з найбільшим значенням до softmax.
- Прихований шар — softsign `x / (1 + |x|)`: лише додавання, ділення й модуль, які IEEE 754 округлює однаково на будь-якій машині. `Math.Tanh` і `Math.Exp` на Windows і Linux можуть відрізнятися в останньому знаку, і тоді розпакування на іншому комп'ютері розійшлося б із запакуванням.
- Одна модель, навчена на train-файлах `Datasets/` (3 епохи, до 2048 позицій з файлу, seed 1, 9 с) і вбудована в збірку. Закодовані дані: 8 байтів `ModelId` (початок SHA-256 від форми й усіх ваг), далі по одному залишку на байт. Дані від іншої моделі відхиляються з помилкою, а не розкодовуються у сміття.
- Експеримент `prediction-experiment` на valid-файлах (модель їх не бачила): ентропія й розмір після LZ77 + Гаффмана для файлу і для залишків; результати — у `PredictionResults`. Підключення до запису архіву — на CP3 разом з Інтеграцією.

# Рішення: Інтеграція (Учасник 4), Чекпоінт 2

## 29. Аналіз і стиснення в запису архіву

**Проблема.** `ArchiveWriter` писав усе без стиснення, а аналізатор (`IFileAnalyzer`) і `Lz77CompressionService` лежали окремо. Треба, щоб шум і вже стиснені файли мали стиснений розмір рівно початковий, а решта справді стискалася.

**Варіанти.** (а) стискати все, а потім дивитися, чи вигідно; (б) спитати аналізатора, стискати за його стратегією, а блок без виграшу все одно зберігати як є.

**Рішення.** (б). `ArchiveWriter(blockSize, analyzer, parseMode, splitMode)`: без аналізатора поведінка як на CP1 (усе як є, байти тому ті самі, тести CP1 не змінилися). З аналізатором `Prepare` для кожного файлу викликає `Analyze`, тип береться від аналізатора, лише якщо у вході він `Unknown`. Стратегія `NoCompression` дає сирі блоки, тож `coded_len = raw_len` і сума стиснених розмірів дорівнює розміру файлу. Стратегія `Lz77Huffman` кодує блоки через `PrepareFixedBlocks` (за замовчуванням лінивий розбір) або `PrepareDpBlocks` (`BlockSplitMode.Dp`, розмір блока кратний 16 КіБ). Якщо жоден блок файлу не стиснувся, стратегія файлу в таблиці чесно записується як `NoCompression`. Стратегія в заголовку блока своя: `NoCompression` для блока, збереженого як є, `Lz77Huffman` для стиснутого.

**Читач.** Блок `Lz77Huffman` розпаковується через `DecodeBlock`. Перед розпакуванням перевіряється `raw_len` (не більше 16 МіБ, сума блоків не більша за розмір файлу з таблиці), тож підроблений заголовок не змусить виділити гігабайти. Помилки декодера стають `E_CODE`. Файл, позначений `NoCompression`, не може мати стиснутих блоків (`E_PAYLOAD`). Тест на зіпсовані байти перевіряє, що вилітає лише `ArchiveException`.

**Чому.** Помилки несиметричні (рішення 27): стиснути вже стиснене коштує лише часу, бо блок без виграшу все одно зберігається як є. Перевірки до розпакування важливі, бо архів може бути чужим.

## 30. Томи і ДП-рюкзак

**Проблема.** Блоки мають розкластися по томах так, щоб кожен том не перевищував `max_volume_bytes`, а сумарна цінність блоків була найбільшою (FORMAT_SPEC_P2, розділ 7).

**Рішення.** `VolumePacker` іде том за томом. Для тому фіксується таблиця файлів: усі файли, що ще мають блоки, плюс порожні файли в першому томі. Далі `W = max_volume_bytes − 41 − 32 − 4 − (записи таблиці файлів)`: 41 заголовок, 32 HMAC (місткість рахується для захищеного тому), 4 поле `file_count`. Вага блока `coded_len + 15`. Рюкзак 0/1 (`Knapsack.SolveDp`): `best[j]` найбільша цінність при вазі не більше `j`, відновлення через бітову таблицю рішень. Невибрані блоки переходять до наступного тому за тим самим правилом. Якщо повна таблиця забрала всю місткість і жоден блок не влазить, береться лише перший файл, що лишився. Кожен том після запису перевіряється: розмір разом з HMAC не перевищує місткість.

**Цінність.** За типом файлу з таблиці `пріоритети_типів`. Справжнього `team_config.json` у проєкті немає, тому `PackingPriorities.Default` (текст 5, код 5, структуровані 4, растр 3, виконувані 3, стиснене 2, штучні 1) це **заглушка**; `TeamConfig.Load` читає `max_volume_bytes` і `пріоритети_типів` (масив з 7 чисел або об'єкт з ключами 0…6), коли файл з'явиться. Форму файлу припущено.

**Відмінність від специфікації.** Специфікація рахує `41 + 32 + 6` для свого формату payload (`file_count` 2 байти, `block_count`, окрема таблиця блоків). Формат цього проєкту (рішення 1 і 2) має `file_count` на 4 байти і блоки з заголовками в секції даних, тож фіксована частина тут 4 байти. Привести формат payload до FORMAT_SPEC_P2 це окрема робота: при цьому змінюється лише `VolumePacker.FixedOverhead` і запис/читання тому, а рюкзак ні.

**Обмеження ДП.** Таблиця рішень займає 1 біт на клітинку `блоків × (W + 1)`; до 200 млн клітинок (25 МБ) результат точно оптимальний. Для більших задач ваги округлюються вгору, а W вниз: вибір завжди влізе, але може бути трохи гіршим за оптимум. У експериментах проєкту межу не досягнуто.

## 31. Жадібне пакування і порівняння

**Рішення.** `Knapsack.SolveGreedy`: блоки за спаданням цінності на байт ваги, кожен береться, якщо ще влазить (рівні щільності: менша вага, потім порядок). `VolumePacker.Compare` пакує ті самі блоки обома способами. Команда `pack-experiment [датасет] [місткість] [team_config.json]` (меню 7 → 4) аналізує й стискає корпус, друкує таблицю «том × метод» і записує по рядку на том і метод у `PackingResults` (експеримент `Packing`). Томи обох розкладок записуються, читаються назад і звіряються з оригіналами.

**Як читати таблицю.** Обидва методи зрештою розкладають усі блоки, тож сумарна цінність за всі томи однакова. Гарантія ДП стосується кожного тому окремо: для однакової множини блоків цінність тому не менша, ніж у жадібного (перевіряється тестом на довільних задачах і на класичному контрприкладі 60/50/50, де жадібний бере 60, а ДП 90). Далі множини блоків у томів різні, тому порівнювати треба передусім перший том.

## 32. Контрольована помилка, коли блок не влазить у том

**Проблема.** Блок, вага якого більша за місткість тому, неможливо розмістити; без перевірки пакувальник зациклився б або мовчки загубив блок.

**Рішення.** Новий код `E_CAPACITY` (поза списком читача: це помилка пакувальника). `VolumePacker.Pack` перевіряє кожен блок до початку: чи влазить він у том із таблицею, що містить лише його файл. Інакше `ArchiveException(E_CAPACITY)` з повідомленням: який блок, скільки він важить, яка місткість і що робити (збільшити том або зменшити блок). Те саме, коли у томі не вміщується таблиця файлів. Також додано `E_VOLUMES` зі специфікації: `ReadVolumes` відхиляє неповний набір, дублікати номерів і томи з різних архівів до розбору вмісту. CLI показує обидва коди з поясненням.

## 33. Звіт покриття в CI

**Рішення.** `coverlet.collector` уже збирав cobertura. Додано крок `Coverage report` (лише Linux): `reportgenerator` зводить файли всіх тестових проєктів, виключає тести, Avalonia-застосунок і міграції EF Core, пише таблицю в підсумок прогону (`GITHUB_STEP_SUMMARY`) і окремий артефакт `coverage-report` (HTML). Змінна `COVERAGE_MIN_LINE` задає нижню межу покриття рядків; зараз 0 (лише звіт), бо поточного значення ще не знаємо.

**Чому.** Один звіт замість кількох cobertura-файлів показує покриття проєкту в цілому. Межу варто підняти до поточного значення після першого зеленого прогону, щоб покриття не падало непомітно.

# Рішення: Аналіз файлу (Blackcat-404), Чекпоінт 2, продовження

## 34. Експеримент «фіксована стратегія проти стратегії від класифікатора»

**Проблема.** Обов'язковий експеримент CP2: показати, що дає вибір стратегії класифікатором порівняно з фіксованою стратегією, і записати результат у БД. Тепер `ArchiveWriter` уміє і аналіз, і стиснення, тож міряти можна на справжніх архівах.

**Варіанти.** Що порівнювати: лише «фіксована» проти «класифікатор» чи ще й нижню межу без стиснення. Як міряти час, якщо операції тривають мілісекунди: один прогін чи кілька з медіаною.

**Рішення.**
- `StrategyComparison` (Archive) пакує кожну групу `Datasets` в один том трьома способами: **без стиснення**, **фіксована** (кожен файл LZ77 + Гаффман, без аналізу), **класифікатор** (вбудований `FileAnalyzer`), потім розпаковує й порівнює побайтово. Аналізатор передається через `IFileAnalyzer`, тож Archive не залежить від Analysis.
- Кожен вимір спершу виконується раз для «розігріву» (JIT), потім 5 разів; зберігається медіана часу.
- Команда `strategy-experiment` і пункт 5 меню «Експерименти»; результати — у `StrategyResults` (вид експерименту `Strategy`).

Рішення класифікатора «не стискати» економить лише спробу LZ77, а на файлах по 20–60 КБ вона коштує стільки ж, скільки сам аналіз (група 5: 2.3 мс проти 2.4 мс); на решті груп аналіз ознак і прогін мережі додають 1–4 мс. Виграш від класифікатора варто очікувати там, де спроба стиснення дорога: великі вже стиснені файли і повільний ДП-розбір чи ДП-розбиття на блоки. Тому на CP3 стратегія має обирати не лише «стискати чи ні», а й спосіб розбору за типом файлу, а внесок класифікатора треба міряти через компоненту T метрики Q на справжньому корпусі. Обмеження: класифікатор навчався на двох із трьох файлів кожної групи, тож його рішення на цих файлах оптимістичні; на розмір це не вплинуло, бо розміри однакові в усіх групах.

# Рішення: Інтеграція (Учасник 4), Чекпоінт 3

## 35. Повний тракт в одному місці

**Проблема.** Кроки тракту вже були, але розкидані: аналіз і стиснення в `ArchiveWriter`, пакування в `VolumePacker`, шифрування в `ProtectedArchive`. CLI збирав їх по-різному в кожній команді, тож вимір Q, ГА і експерименти не мали єдиної точки входу.

**Рішення.** `ArchivePipeline`: `Prepare` (аналіз, блоки, стиснення), `Seal` (рюкзак, AES-256-CTR, HMAC), `Pack`, `Unpack`. Параметри в `PackOptions`. Старі методи не змінено, їх використовують наявні тести.

**Відхилення від специфікації, яке виправлено.** PBKDF2 (100 000 ітерацій) виконувався для кожного тому окремо, а специфікація каже «один раз на архів». На багатотомному архіві це множило час (T у Q) і давало різні ключі. Тепер сіль спільна, ключі виводяться один раз (`KeyCache`), а унікальність nonce гарантує побудова `8 випадкових байтів ‖ uint32_BE(номер тому)`. Читач відхиляє томи з однаковою парою сіль+nonce.

## 36. Коди помилок замість винятків

`ArchiveException(ErrorCode)` лишається всередині (вона зручна для коду, що кидає глибоко), а на межі тракту `TryUnpack`/`TryExtract` повертають `ArchiveResult` з кодом `E_MAGIC`, `E_LENGTH`, `E_HMAC`, `E_PAYLOAD`, `E_CODE` або `E_CRC` (також `E_VOLUMES`, `E_CAPACITY`). Ловиться лише `ArchiveException`: інші винятки (помилка диска) не маскуються. `BadArchiveTests` будує по одному пошкодженому архіву на код; пошкодження всередині payload запечатуються з вірним HMAC, інакше вони завжди давали б `E_HMAC`. Справжні `bad_*.arc` і `expected_failures.json` викладача кладуться в `tests/SmartArchiver.Archive.Tests/Bad/` і перевіряються тим самим тестом (формат JSON припущено: `{"файл": "КОД"}`, у файлів викладача його варто звірити).

## 37. Атомарне розпакування

`Extract` спершу розпаковує й перевіряє все в пам'яті, потім перевіряє, що жоден цільовий файл не існує, пише файли в тимчасову теку `.extract-…` усередині цільової, і переносить їх `File.Move` без перезапису. Якщо щось іде не так посеред переносу (наприклад, файл з'явився за мить до цього), вже перенесене видаляється, тимчасова тека і створена порожня цільова теж. Недолік: пам'ять під усі файли архіву одночасно; для курсового корпусу це прийнятно.

## 38. Автоматичний вимір Q

`CorpusMeasurer.Measure` проганяє весь корпус через тракт (запакувати → зашифрувати → розпакувати), міряє час лише тракту, звіряє кожен файл побайтово. `Q = α·S + β·T`, `S = B_orig / (B_orig + B_arc)`, `T = t_ref / (t_ref + t)`, `Q = 0`, якщо хоч один файл не відновився. `B_arc` це розмір усіх томів із шифруванням і HMAC. Команда `measure` пише `MeasurementRun` і `MeasurementFileResult` (групи без імен файлів і без пароля). **Заглушки:** значення α, β, `t_ref` і місткість тому за замовчуванням (0.5, 0.5, 1 с, 256 КБ) вигадані, справжні мають прийти з `team_config.json`; без нього команда друкує попередження.

## Не зроблено (завдання 6 «крос-сумісність»)

Формат ще відрізняється від `FORMAT_SPEC_P2` у деталях (`file_count` як u32, нумерація томів з 1, лічильник CTR з 0, немає `E_SHORT`, дозволено `Unknown`=255). Для відкриття чужого архіву це треба звіряти з їхнім кодом.

Рішення: Стиснення (Артем / keytrw), Чекпоінт 3

Цей розділ доповнює рішення 9–13 (CP1) і 20–25 (CP2). Умови чотирьох завдань збережено за командним планом чекпоінтів. Числові результати нижче — з фактичних запусків на командному корпусі; за зміни файлів або параметрів їх потрібно вимірювати заново.

39. Перевірка стиснення на всіх семи групах: повний round-trip та CRC32
Проблема. У CP2 були тести окремих парсерів і блокових кодерів, але цього недостатньо, щоб довести, що повний архів із реальними файлами розпаковується без втрати або перестановки байтів. Завдання CP3 вимагає перевірити всі сім груп корпусу й збіг CRC32.

Варіанти. (а) перевіряти лише Lz77BlockEncoder/Lz77BlockDecoder; (б) створювати справжні архіви через ArchiveWriter, читати їх через ArchiveReader і порівнювати результат із джерелом.

Рішення. (б). Додано корпусні інтеграційні тести на 22 файлах із груп 0–6. Для перевірюваних режимів стиснення архів збирається і читається назад; зіставляються імена, довжини й вміст байт у байт, а контрольні суми CRC32 мають відповідати оригіналам. Перевіряються зокрема фіксоване розбиття й ДП-розбиття на блоки. Тест використовує реальний тракт архіву, а не тільки окремий кодек.

Чому. Окремий unit-тест може не виявити помилку у зв'язуванні блока з файлом, його межах або службовому записі. Наскрізний round-trip перевіряє сумісність Compression із Archive, а CRC32 додає незалежну перевірку цілісності. Корпусний тест доцільно тримати в тестовому проєкті Archive; якщо файл фізично лежить серед тестів Compression, потрібно явно виключити його з однієї збірки й підключити до іншої в .csproj, щоб не створювати дублювання або неправильні залежності.

Результат і межа відповідальності. Для використаного корпусу перевірки пройшли. Це не твердження про повну сумісність із чужими архівами: питання крос-сумісності та окремі невідповідності FORMAT_SPEC_P2 залишаються в компетенції інтеграції (див. рішення 35–38).
40. Ітеративний DP із вартостями Huffman (D1 №19)
Проблема. Початковий DpParser із CP2 мінімізував умовну вартість: літерал — 9 біт, посилання — 17 + max(0, bit_length(dist − 1) − 1) біт. Реальний розмір залежить від частот LIT/LEN/DIST, довжин кодів Huffman і таблиць у блоці. Тому найкращий розбір за фіксованою моделлю не обов'язково найкращий після кодування.

Варіанти. (а) лишити фіксовану модель; (б) перераховувати DP за актуальними довжинами кодів Huffman і приймати результат без перевірки; (в) так само перебудовувати коди, але приймати лише фактично менший закодований блок.

Рішення. (в). Уведено ParseCostModel із фіксованою моделлю та моделлю, одержаною з Huffman-довжин, і IterativeParser. Ітерація виконує послідовність: початковий DP → фактичне Huffman-кодування → нові довжини LIT/LEN/DIST → повторний DP → повторне кодування → порівняння довжин реальних закодованих блоків. Найкращий результат зберігається; невдала ітерація не замінює його. Встановлено обмеження на кількість ітерацій і зупинку за відсутності поліпшення. Вартість DP оптимізовано, щоб не перебирати всі довжини збігів на кожній позиції без потреби.

Зворотна сумісність. Старий виклик DpParser.Parse(block) залишено як виклик із ParseCostModel.Fixed(). Новий режим інтегровано в Lz77CompressionService, тому Archive не повинен знати деталі ітеративного алгоритму. Кодер у форматі архіву залишається канонічним Huffman.

Результат на корпусі (22 файли, 7 груп; блок 8 КіБ, maxChain = 32, максимум три додаткові ітерації):
Ітерація	Сумарний прийнятий розмір, Б	Додаткова економія, Б	Час виміряних операцій, с
0 — початковий DP	231 592	—	3,9310
1	230 632	960	4,0297
2	230 449	183	2,2083
3	230 424	25	0,8787


Разом зекономлено 1 168 Б (0,50%). Додатковий виграш спадає (960 → 183 → 25 Б), і прийнятий результат не зростає завдяки порівнянню реальних довжин. За інших розмірів блоків або глибини пошуку числа інші; результати різних конфігурацій безпосередньо порівнювати не можна. Сума наведених часів — час виміряних етапів бенчмарка, а не гарантовано повний час команди CLI.

Чому. Повторне оцінювання вартостей підлаштовує вибір LZ77-токенів під фактичний Huffman, а перевірка закодованих байтів захищає від ситуації, коли вдаліший за моделлю розбір дає гірший розмір через таблиці та вирівнювання. Умова незростання стосується прийнятого результату відносно початкового DP за тих самих параметрів, а не обов'язково кожної кандидатної ітерації.
41. Збереження експериментів CP3 через наявну БД без окремих таблиць і CSV
Проблема. Для ітеративного DP та порівнянь потрібно зберігати параметри й результати, але нові EF Core-сутності, таблиці та міграції заради одного експерименту ускладнювали б зону Data, за яку відповідає інший учасник. Для цього чекпоінту детальний експорт CSV було вирішено прибрати.

Варіанти. (а) створити окремі таблиці файлів та ітерацій; (б) повторно використати Experiment / IMeasurementStore.SaveExperiment() і серіалізувати підсумки в ParametersJson; (в) зберігати лише CSV.

Рішення. (б) для експериментальних команд CP3. На рівні ConsoleApp використовується наявний OpenMeasurementStore() і SaveExperiment(). Запис має ExperimentKind.Parsing, а конкретний вид визначається полем experimentType у JSON, наприклад IterativeDp; у JSON також потрапляють параметри, сумарні результати, дані по файлах та агреговані ітерації. Для арифметичного експерименту та ZIP-бенчмарка застосовується той самий підхід із власними позначками виду експерименту. Compression не залежить від Data. Виклик SaveCsv() для ітеративного DP прибрано; остаточні експериментальні режими не потребують створення CSV.

Чому. Один запуск можна записати без зміни схеми SQL Server і без втручання в чужі міграції. Недолік — поле ParametersJson містить не лише параметри, а й результати; база не перевіряє типи й діапазони вкладених значень через окремі CHECK. Це свідомий компроміс для дослідницьких експериментів, а не заміна типізованих таблиць ParsingResults та інших результатів CP2.

42. Експериментальне арифметичне кодування замість Huffman — лише для порівняння
Проблема. Потрібно виміряти, скільки коштує використання Huffman замість арифметичного кодування, але специфікація SARC вимагає лишити Huffman у звичайному архіві. Порівнювати кодери на різних LZ77-розборах некоректно.

Варіанти. (а) замінити Huffman у SARC; (б) окремо закодувати однакові LZ77-токени двома способами; (в) порівнювати лише теоретичну ентропію без кодування.

Рішення. (б). Додано експериментальний ArithmeticBlockCodec із кодером та декодером і ArithmeticBenchmark. Обидва кодери отримують ті самі токени й три алфавіти LIT, LEN, DIST; вимірюються payload (бітовий потік) і повний блок (payload разом із таблицями та заголовками). Перевіряється точний round-trip. ArchiveWriter, ArchiveReader і формат SARC не переведено на Arithmetic.

Представлення моделі. У випробуваному стандартному Arithmetic для кожного присутнього символу таблиці частот зберігають ідентифікатор і частоту (по 2 байти), тоді як формат таблиць канонічного Huffman передає компактні довжини кодів. Це зменшує перевагу арифметичного бітового потоку на повному розмірі.

Фінальний результат (22 файли, 930 262 вхідних байти; блок 64 КіБ, maxChain = 256, три ітерації DP):
Показник	Huffman, Б	Arithmetic, Б
Payload	190 647	189 478
Таблиці й заголовки	8 973	11 830
Повний обсяг	199 620	201 308


Арифметичний payload менший на 1 169 Б (~0,61% від Huffman payload), але службові дані більші на 2 857 Б. У результаті повний арифметичний потік більший на 1 688 Б (~0,85% від повного Huffman). За повним розміром Huffman переміг у шести групах із семи; в групі 6 Arithmetic був меншим на 205 Б. За розміром payload Arithmetic переміг у всіх семи групах.

Чому. Арифметичне кодування краще наближає потік символів до їхніх імовірнісних вартостей, проте на цьому корпусі додаткові байти частотних таблиць переважили економію. Це висновок про конкретну реалізацію та її формат таблиць, а не доведення загальної переваги Huffman над арифметичним кодуванням.
43. Прибирання зайвого доповнення арифметичного потоку та відмова від Compact-формату
Проблема. Початкова експериментальна реалізація після ArithmeticEncoder.Finish() безумовно дописувала 32 нульові біти: декодер вимагав їх через суворий BitReader. Це створювало зайві 4 байти на блок, які не несли корисних даних. Окремо розглядали оптимізацію самих таблиць частот через Bitmap + VarInt.

Варіанти. (а) зберігати 32 нульові біти; (б) дозволити арифметичному декодеру читати віртуальні нулі за фізичним кінцем бітового потоку, не змінюючи суворий ReadBit() для Huffman; (в) додатково змінити формат частотних таблиць на Compact.

Рішення. (б). У BitReader додано окремий ReadBitOrZero() для потреб арифметичного декодера, а безумовний виклик WriteBits(0, 32) із Finish() вилучено. Звичайний ReadBit() лишився суворим. У тестах виправлено помилки компіляції, пов'язані з ref struct/scoped ref, а також попередження аналізатора CA1832 та відсутній using для ArchiveException.

Виміряний ефект. У конфігурації 8 КіБ видалено 512 Б (= 128 блоків × 4 Б); у конфігурації 64 КіБ — 108 Б (= 27 блоків × 4 Б) на відповідному повторному запуску. Кодер після зміни проходив побайтовий round-trip на корпусі. Арифметичний декодер із віртуальними нулями має відмінні від Huffman властивості виявлення обрізаних потоків; це прийнятно для експериментального кодера й не змінює контроль помилок SARC.

Відхилений варіант. Для Arithmetic Compact було підготовлено варіант із Bitmap + VarInt і короткими списками символів для розріджених таблиць. Остаточно вирішено не залишати його в підсумковій реалізації, а аргументувати базовий арифметичний формат. Тому вимірів Compact як підтвердженого результату чекпоінту немає; у висновках застосовуються числа стандартного Arithmetic після виправлення 32-бітного доповнення.
44. Бонус CP3 №4: порівняння реального SARC з ZIP і межа досягнутого
Проблема. Бонус формулюється як «обігнати zip -9 на корпусі». Порівняння тільки закодованих блоків нечесне: у справжніх архівах є таблиці файлів, заголовки, блокові записи та інші витрати. На машині розробки було незручно встановлювати зовнішню утиліту zip.

Варіанти. (а) порівнювати тільки payload; (б) створювати повні ZIP і SARC із перевіркою розпакування, використовуючи зовнішній zip -9; (в) замість зовнішньої утиліти користуватися вбудованим System.IO.Compression.ZipArchive з CompressionLevel.SmallestSize, явно позначивши відмінність від zip -9.

Рішення. (в) для локального експерименту. Zip9Benchmark розміщено в SmartArchiver.Compression/Benchmarks, але він не посилається напряму на Archive: створення й перевірка SARC передаються делегатом з CLI, щоб не виникло циклічної залежності Archive → Compression → Archive. Порівнюються повні архіви на однаковому корпусі, а обидва формати перевіряються побайтовим round-trip. Без CSV; підсумки виводяться в CLI та можуть зберігатися через наявний SaveExperiment() за наявності БД.

Перевірені режими SARC: продуктовий Lazy/64 КіБ; Iterative/64, 128 і 256 КіБ; DP Block Splitter/64 КіБ. Результати повного корпусу (22 файли, 930 262 Б):
Режим	Розмір архіву, Б	Час створення SARC, с
ZIP (.NET SmallestSize)	192 969	—
SARC Lazy / 64 КіБ	201 905	0,331
SARC Iterative / 64 КіБ	199 150	27,065
SARC Iterative / 128 КіБ	198 129	27,540
SARC Iterative / 256 КіБ	198 129	28,341
SARC DP Block Splitter / 64 КіБ	203 904	0,444


Результат. Найменший SARC отримано з Iterative DP/128 КіБ (такий самий розмір з 256 КіБ); до ZIP .NET залишилося 5 160 Б, або 2,67% від розміру ZIP. На окремо заархівованих групах код (група 1) та структуровані дані (група 2) були кращими за ZIP відповідно на 388 Б і 1 405 Б. Найбільше відставання зафіксовано на растрах (група 3, 4 772 Б) та бінарних файлах (група 4, 2 144 Б). Результати груп не можна додавати для одержання результату спільного архіву, оскільки в кожній групі заголовки повторюються. Причини відставання (інший пошук LZ77-збігів, службові дані, представлення довжин/відстаней) залишаються гіпотезами без покомпонентного профілювання.

Чому. Великий блок зменшує витрати на таблиці, а Iterative DP враховує Huffman-вартості, однак збільшує час: 27,540 с проти 0,331 с у Lazy при виграші за розміром 3 776 Б. Подальше збільшення блока до 256 КіБ не зменшило архів. Запропонований вибір найкращого режиму окремо для кожного файла (Adaptive / best per file) не ввійшов до підсумкового коду за ухваленим рішенням залишити бонус без додаткових змін.

Статус бонусу. Бенчмарк реалізовано, близькість до ZIP показано, але ціль «обігнати zip -9» не виконано і безпосередньо zip -9 у фінальному запуску не виміряно. Правильна назва еталона у звіті й комітах: ZIP (.NET SmallestSize), а не zip -9. Для остаточного доведення бонусу знадобилося б окреме порівняння з реальною утилітою zip -9 на точно тому самому корпусі.

# Рішення: Аналіз файлу і База даних (Blackcat-404), Чекпоінт 3

## 45. Журнал еволюції ГА в БД і в CSV

**Проблема.** ГА (`kycile24`) запускається після нашого кроку, і план вимагає, щоб журнал еволюції був у БД ще до першого запуску: покоління, пристосованість, хромосоми, а копія журналу має лежати в репозиторії. З журналу будується обов'язкова таблиця звіту «збіжність ГА проти випадкового пошуку», а на експертному рівні ще й фронт Парето.

**Варіанти.** (а) Зберігати лише найкращу і середню пристосованість покоління. (б) Зберігати кожну перевірену хромосому. Для генів: окрема колонка на кожен ген, окрема таблиця «ген = значення» або JSON-об'єкт в одній колонці.

**Рішення.** (б): таблиця `GeneticIndividuals`, один рядок на хромосому, експеримент виду `Genetic`. У рядку є алгоритм (`Genetic`, `Random`, `LocalSearch`), покоління, номер особини, гени як JSON-об'єкт, пристосованість і окремо S та T. ГА і випадковий пошук пишуться в той самий експеримент, тож порівняння береться з одного запуску. Для випадкового пошуку «покоління» означає пакет такого ж розміру, як популяція ГА, тому однакова кількість обчислень пристосованості видна прямо з таблиці. Обмеження CHECK: покоління й номер ≥ 0, пристосованість ≥ 0, S і T у межах 0…1, гени є JSON-об'єктом (`ISJSON`). Унікальний індекс не дає записати ту саму особину двічі. CSV вивантажує команда `export-ga`: фіксовані колонки, далі по колонці на ген у порядку першої появи; числа записуються в інваріантній культурі, а рядки закінчуються `\n`, тож файл однаковий на будь-якій машині.

**Чому.** Найкраща й середня по поколіннях виводяться з повного журналу одним запитом, а навпаки не вийде: фронт Парето потребує S і T кожної хромосоми. Обсяг малий (30 особин × 50 поколінь дають 1 500 рядків). Гени лежать у JSON, бо хромосома буває з 3 генів (базовий рівень) і повна (просунутий: глибина пошуку, розмір блоку, k, архітектура перцептрона, прапорці). Окрема колонка на ген вимагала б міграції на кожну зміну хромосоми, а таблиця «ген = значення» множила б кількість рядків, не даючи нових перевірок. Недолік JSON у тому, що база не перевіряє діапазони окремих генів, але це вже робить сам ГА, коли будує хромосому. Алгоритм ГА нічого не знає про БД: він повертає записи, а CLI зберігає їх через `IMeasurementStore`, як і в експериментах CP2.

## 46. Історія архівацій без імен, паролів і ключів

**Проблема.** Потрібна історія архівацій, яку потім покаже екран Avalonia: що і коли запаковано чи розпаковано і чим це закінчилося. Умова: у базі не повинно бути паролів, ключів і відкритих імен файлів. Крім того, архівація не повинна залежати від бази.

**Варіанти.** Що записувати: лише успішні операції чи всі. Як захистити від імен: фільтрувати їх перед записом або не мати для них місця в схемі. Як поводитися, коли база недоступна: зупиняти `pack` і `unpack` чи лише попереджати.

**Рішення.** Таблиця `ArchiveOperations`, один рядок на кожен `pack` чи `unpack`, зокрема невдалий. У рядку є дата, операція, кількість файлів і скільки з них стиснуто, розмір файлів і архіву, кількість томів, час, успіх і код помилки. Коди помилок: `E_*` з формату (наприклад, `E_HMAC` при хибному паролі, `E_CAPACITY`, коли блок не влазить у том), `E_IO`, коли `unpack` знайшов наявний файл, і `E_VERIFY`, коли після запакування контрольне читання не збіглося з оригіналом. Єдина текстова колонка таблиці містить код помилки, а тест перевіряє, що інших текстових полів у сутності немає. Обмеження CHECK: код є тоді й лише тоді, коли операція не вдалася; кількість стиснених файлів не більша за кількість файлів; розміри, кількість томів і час ≥ 0. Запис іде з CLI після операції. Якщо база вимкнена, нічого не пишеться, а якщо недоступна, з'являється попередження, і архівація все одно завершується успішно. Команда `history [кількість]` показує останні операції.

**Чому.** Ім'я, якого немає де зберегти, не потрапить у базу навіть через помилку в коді. Фільтр перед записом такої гарантії не дає. Невдалі операції теж корисні: в історії видно, наприклад, кілька `E_HMAC` поспіль. Під час розробки тест знайшов помилку в першій версії CHECK. Умова `LEN([ErrorCode]) > 0` для NULL дає в SQL не «хибно», а «невідомо», а CHECK пропускає «невідомо», тож невдала операція без коду проходила. Тепер умова явно містить `[ErrorCode] IS NOT NULL`. Недолік: якщо базу налаштовано, але сервер вимкнено, `pack` чекає тайм-аут підключення SqlClient (близько 15 с) і лише потім попереджає. Архів при цьому створюється правильно. Скоротити очікування можна параметром `Connect Timeout` у рядку підключення.

## 47. Дані для 5 обов'язкових таблиць звіту

**Проблема.** Звіт має 5 обов'язкових таблиць, і Інтеграція на кроці 6 будує їх однією командою з БД. Для трьох таблиць дані вже були (`ParsingResults`, `PackingResults`, журнал ГА), для двох не було: «вплив кожного блоку» (Q з вимкненим по черзі блоком тракту) і «стиснути → зашифрувати» проти зворотного порядку. До того ж експерименти виду `Parsing` бувають різні: ітеративний ДП, арифметичне кодування і порівняння з ZIP (рішення 41) зберігають результати лише в JSON, тож «останній експеримент виду» може не мати рядків для таблиці.

**Варіанти.** (а) Генератор звіту сам читає сутності й рахує таблиці. (б) Шар даних дає готові рядки кожної таблиці, а генератор їх лише форматує. Для двох нових таблиць: зберігати їх у JSON, як рішення 41, або окремими таблицями з обмеженнями.

**Рішення.** (б) і окремі таблиці. `BlockImpactResults`: один рядок на вимкнений блок (`None` означає повний тракт і є базою порівняння, далі `Analysis`, `Lz77`, `Huffman`, `Packing`, `Encryption`, `Prediction`), розміри, час, S, T, Q. CHECK: S і T у межах 0…1, а `Q = 0`, якщо не все відновлено, як того вимагає визначення метрики; унікальний індекс не дає виміряти той самий блок двічі в одному експерименті. `EncryptionOrderResults`: група, розмір файлу і розмір у кожному з двох порядків. `ReportTables` рахує рядки: коефіцієнт стиснення для розбору; зміну Q відносно повного тракту для блоків; лише перший том і заповненість у відсотках для пакування; суми по групах і обидва коефіцієнти для порядку шифрування; для ГА найкращу, середню й найкращу досі пристосованість по поколіннях разом із накопиченою кількістю обчислень пристосованості. `ReportData.Load` бере для кожної таблиці найновіший експеримент свого виду, у якому є рядки, і додає номер, дату й коміт цього експерименту.

**Чому.** Як рахувати рядки, вирішує зона даних, а генератор звіту лише форматує: так обчислення покриті тестами без БД, а таблиці в звіті збігаються з тим, що лежить у базі. Номер і коміт експерименту біля кожної таблиці дають змогу відтворити її, як того вимагає журнал запусків. Накопичена кількість обчислень робить порівняння ГА з випадковим пошуком чесним, бо умова вимагає однакової кількості обчислень пристосованості. Окремі таблиці замість JSON дають CHECK-обмеження. **Що лишається іншим:** експеримент «вплив блоків» запускає і пише в `BlockImpactResults` Інтеграція. Експеримент порядку шифрування (`EncryptionCompressionExperiment`, `kycile24`) поки міряє через GZip і в БД не пише. Для таблиці звіту його варто перевести на наш LZ77 + Гаффман: GZip допустимий лише як еталон з позначкою. Результати треба записати в `EncryptionOrderResults`.
