# Рішення: Інтеграція (hrabovskaol-ai), Чекпоінт 1

Формат: проблема → варіанти → рішення → чому.

## 1. Розкладка 41-байтового заголовка тому

**Проблема.** У методичці сказано лише, що відкритий заголовок має 41 байт і містить magic, версію, номер/кількість томів, salt, nonce, ciphertext_len. Точні розміри й порядок полів у FORMAT_SPEC_P2.md.

**Варіанти.** (а) чекати специфікацію; (б) вивести розкладку з суми розмірів і зробити її змінюваною в одному місці.

**Рішення.** (б): `magic(4) "SARC" | версія(1) | номер тому(2) | кількість томів(2) | salt(16) | nonce(12) | ciphertext_len(4)`, усе big-endian, номер тому з 1.

**Чому.** 4+1+2+2+16+12+4 = 41, тобто сума збігається, а salt(16) і nonce(12) задані методичкою. Порядок полів, ширина полів номера/кількості томів і нумерація з 1 це припущення. **Потрібно звірити з FORMAT_SPEC_P2.md до merge.** Усе зосереджено в `FormatConstants.cs` і `VolumeHeader.cs`, а `VolumeHeaderTests.Write_ProducesExactBytes` фіксує байти.

## 2. Службовий заголовок блока: 15 байт

**Проблема.** Вага блока в рюкзаку = `coded_len + 15`, але звідки 15, методичка не пояснює.

**Варіанти.** (а) довільні 15 байт; (б) мінімальний набір полів, який дає саме 15.

**Рішення.** (б): `file_index(2) | block_index(4) | raw_len(4) | coded_len(4) | стратегія(1)` = 15.

**Чому.** Блоки мають бути самоописними: при пакуванні в томи вони підуть не по порядку, тож треба знати файл і номер блока. `coded_len` окремо від `raw_len` потрібен для стиснення. Стратегія на рівні блока залишає місце для адаптивної стратегії всередині файлу (експертний рівень Blackcat-404). Те саме потрібно звірити зі специфікацією.

## 3. Помилки: ArchiveException з кодом

**Проблема.** Для bad\_\*.arc потрібні коди E_MAGIC, E_LENGTH, E_HMAC, E_PAYLOAD, E_CODE, E_CRC. У CP3 вони мають замінити винятки.

**Варіанти.** (а) Result-тип одразу; (б) один виняток з полем `Code`.

**Рішення.** (б): `ArchiveException(ErrorCode, message)`. Версія формату, що не збігається, дає E_MAGIC (окремого коду для неї в списку немає).

**Чому.** Усередині парсера виняток простіший, ніж протягувати Result крізь кожен виклик. Верхній рівень (CLI, CP3) перетворить його на код. Тести перевіряють, що на будь-якому зіпсованому вході вилітає лише `ArchiveException`, а не `IndexOutOfRange` чи `OutOfMemory`.

## 4. Власний CRC32

**Проблема.** CRC32 потрібен для кожного файлу. У .NET він є лише в окремому NuGet-пакеті.

**Рішення.** Власна табличка (поліном 0xEDB88320), тест на вектор `"123456789" → 0xCBF43926`.

**Чому.** Це 20 рядків, а додаткових залежностей у тракті методичка не любить (зовнішні бібліотеки дозволені лише для AES, SHA-256, файлів, графіків і тестування).

## 5. Безпечні імена

**Проблема.** Path traversal при розпакуванні.

**Рішення.** Імена перевіряються і при записі, і при читанні (`SafeNames`). Відхиляються: порожнє, `/ \ :` NUL, імена лише з крапок (`.`, `..`, `...`), понад 255 байт UTF-8, некоректний Unicode. Дублікати імен в одному архіві теж відхиляються. Код помилки E_PAYLOAD, як у методичці.

**Чому.** Заборона роздільників вже виключає шляхи, а «лише крапки» додатково закриває `...`, яке Windows спрощує до порожнього імені. Перевірка саме на читанні важлива, бо архів може бути чужим або підробленим.

## 6. CI

**Проблема.** Кожна зміна має перевірятися автоматично.

**Рішення.** GitHub Actions: збірка й тести на кожен PR і пуш у main, матриця ubuntu + windows, кеш NuGet, скасування застарілих прогонів, TRX і coverage як артефакти. Потрібно вручну (Settings → Branches → main): увімкнути **Require status checks** і додати обидві перевірки `build & test (...)`.

**Чому.** Команда може працювати на різних ОС (шляхи, роздільники рядків), тож один Linux-прогін це пропустив би. Без обов'язкових перевірок у гілці main «CI на кожен PR» лише декоративний.

# Рішення: База даних (Blackcat-404), Чекпоінт 1

## 7. СУБД і спосіб доступу до неї

**Проблема.** Уже на CP1 базове Q треба записати в БД, а на CP2–CP3 туди підуть експерименти, журнал ГА, прогони навчання класифікатора й історія архівацій, і з неї будуватимуться 5 таблиць звіту. Схема ростиме з кожним чекпоінтом, а на CP2 шар доступу має дати параметризовані запити, транзакції й обмеження цілісності.

**Варіанти.** СУБД: (а) SQLite, файл поруч із програмою, нічого не треба встановлювати; (б) PostgreSQL; (в) MS SQL Server. Доступ: (г) ADO.NET і SQL вручну; (ґ) EF Core з міграціями.

**Рішення.** (в) + (ґ): MS SQL Server через EF Core, схема задається кодом (`src/SmartArchiver.Data`). Програма сама застосовує міграції при першому зверненні до БД (`Database.Migrate()`), окремих SQL-скриптів немає. На CP1 у схемі дві таблиці: `MeasurementRuns` (прогін вимірювання Q з полями журналу прогону: дата, коміт, seed, параметри, набір даних, результат, час) і `MeasurementFileResults` (результат по кожному файлу). Решта таблиць додаватиметься новими міграціями.

**Чому.** Міграції EF Core дають версіоновану схему: кожна зміна є окремим файлом у git, а в кожного учасника база оновлюється сама. Вимоги CP2 закриваються штатно: запити EF Core параметризовані, один `SaveChanges` виконується однією транзакцією, ключі, NOT NULL і CHECK описуються в моделі. SQL Server має повноцінні транзакції й обмеження та зручні інструменти, щоб показати дані на захисті, а в Docker він однаково запускається на Windows, Linux і macOS. Мінус у тому, що потрібен запущений сервер, на відміну від SQLite. Це закриває рішення 8. Обмеження методички на зовнішні бібліотеки стосуються тракту архівації. БД живе поруч із ним і не торкається ні формату архіву, ні самого стиснення. Якщо від SQL Server доведеться відмовитися, EF Core підтримує й SQLite: зміниться провайдер і міграції, а не код, що пише результати.

## 8. БД необов'язкова, і кожен налаштовує свою

**Проблема.** У кожного учасника свій SQL Server зі своїм паролем, а рядок підключення з паролем не можна комітити. Проєкт має запускатися з README без втручання автора (E3). Тести й CI не повинні падати там, де сервера немає (Windows-раннер GitHub не запускає Linux-контейнери).

**Варіанти.** (а) один спільний рядок підключення в `appsettings.json` у git; (б) рядок у змінній середовища; (в) `appsettings.json` у git з порожнім рядком плюс особистий `appsettings.Local.json` поруч, доданий у `.gitignore`.

**Рішення.** (в). Порожній рядок означає, що БД вимкнена: сховище приймає виклики й нічого не пише. До сервера звертаються лише ті команди, яким потрібна БД (зараз це `db`), тож `pack`, `unpack`, `info` і `demo` працюють і без SQL Server. Рядок без `Database=` відхиляється, інакше таблиці потрапили б у `master`. Помилки БД перетворюються на `DatabaseException`, у повідомленні якої є сервер і назва бази, але немає пароля, а CLI повертає код 4. Тести, яким потрібен сервер, позначені `[DatabaseFact]`: вони виконуються лише тоді, коли задано змінну `SMARTARCHIVER_TEST_SQLSERVER`, і кожен працює у власній тимчасовій базі, яку видаляє після себе. У CI Linux-задача піднімає SQL Server у контейнері з паролем, згенерованим на кожен прогін, а Windows-задача ці тести пропускає.

**Чому.** Пароль не потрапляє в git, і кожен підключається до свого сервера, нічого не змінюючи в спільних файлах. Файл поруч із програмою простіший за змінну середовища: однаково працює на всіх ОС і при запуску з IDE, і його видно. Архіватор, який перевіряють кейси C1 і запуск з README, не залежить від того, чи піднятий SQL Server. Окрема база на кожен тест означає, що тести не залежать від даних один одного і не псують робочу базу.

# Рішення: Стиснення (keytrw), Чекпоінт 1

## 9. Формат таблиці довжин кодів у блоці

**Проблема.** Декодер Гаффмана відновлює коди з довжин, записаних у блок. Точний байтовий формат таблиці задає FORMAT_SPEC_P2.md, якого команді не надали.

**Варіанти.** (а) таблиця фіксованого розміру 256 байт, індекс = символ, 0 означає «не використовується»; (б) розріджена таблиця: бітова карта використаних символів (32 байти) + довжини лише для них; (в) довжини кодуються окремим Гаффманом поверх довжин, як у DEFLATE.

**Рішення.** (а): `lengths[256]`, `lengths[s]` — довжина коду символу `s`.

**Чому.** Найпростіша реалізація для CP1, де алфавіт — усі байти 0…255, декодеру нічого зіставляти. Варіанти (б) і (в) ефективніші за розміром, але не потрібні для першого чекпоінту. **Потрібно звірити з FORMAT_SPEC_P2.md до merge**, особливо якщо специфікація вимагає окремих алфавітів LIT/LEN/DIST (методичка, 10.22) — тоді формат міняється на CP2. `TableSize` винесено як константу саме для цього переходу. Усе зосереджено в `HuffmanCodec.cs` і `HuffmanLengths.cs`.

## 10. Порядок бітів у закодованому потоці

**Проблема.** Без FORMAT_SPEC_P2.md невідомо, старший чи молодший біт коду йде першим, і чим доповнюється останній неповний байт.

**Варіанти.** (а) старший біт першим (MSB-first), доповнення нулями; (б) молодший біт першим (LSB-first), як у DEFLATE.

**Рішення.** (а).

**Чому.** Найпоширеніший порядок для навчальних реалізацій і узгоджується з прикладом з методички (6.5). Позначено як припущення в `BitIo.cs`; якщо специфікація вимагає іншого порядку, міняється лише цей файл, решта кодека від напрямку бітів не залежить.

## 11. Порожній вхід у HuffmanCodec.Encode

**Проблема.** Порожня таблиця довжин не проходить перевірку рівності Крафта (`CanonicalHuffman.AssignCodes`), тож порожній блок закодувати напряму не можна.

**Варіанти.** (а) `Encode` кидає `ArgumentException`: виклик з порожнім блоком — помилка виклику, Writer не створює блоків для порожніх файлів; (б) `Encode` повертає порожній результат, `Decode` з `rawLength = 0` повертає порожній масив.

**Рішення.** (а).

**Чому.** Узгоджується з тим, як уже працює `ArchiveWriter`: порожній файл не має жодного блока (`offset = 0`, блоків 0). Кодек на порожньому вході в реальному архіві ніколи не повинен викликатися, тож така ситуація — помилка виклику (`ArgumentException`), а не пошкоджені дані архіву (`ArchiveException`).

## 12. Видимість internal-класів кодека для тестів

**Проблема.** `CanonicalHuffman`, `HuffmanLengths`, `HuffmanCodec`, `BitWriter`, `BitReader` — деталі реалізації, не частина публічного API `SmartArchiver.Core`, але тестам (`SmartArchiver.Core.Tests`) потрібен прямий доступ до них.

**Варіанти.** (а) зробити класи `public`; (б) лишити `internal`, дати доступ тестовій збірці через `InternalsVisibleTo`.

**Рішення.** (б): `InternalsVisibleTo` на `SmartArchiver.Core.Tests` у `SmartArchiver.Core.csproj`.

**Чому.** API `SmartArchiver.Core` лишається мінімальним: зовнішній код працює лише через `ArchiveWriter`/`ArchiveReader`, не залежить від внутрішньої структури кодека, яку доведеться переробити на CP2 під алфавіти LIT/LEN/DIST.

## 13. Тести, відкладені через структуру поточного формату таблиці

**Проблема.** Методичка (6.5, п'ята перевірка) вимагає тестів на довжину коду 0 для використаного символу, дубльований символ і символ поза алфавітом. У поточному форматі (таблиця з 256 записів, індекс = символ) усі три ситуації структурно неможливі.

**Рішення.** Тести не написано на CP1.

**Чому.** Тестувати неможливу в поточному коді ситуацію означало б тестувати вигадану поведінку. Повернутися до цього пункту, якщо формат стане розрідженим (п. 9, варіант б) або з'являться окремі алфавіти LIT/LEN/DIST на CP2.

# Рішення: Архітектура (Blackcat-404), після Чекпоінту 1

## 14. Проєкт на кожну зону

**Проблема.** Усі зони лежали в одному проєкті Core, а їхні тести — в одному Core.Tests. 13.10 файл однієї зони (`ArchiveSecurity.cs`) не потрапив у коміт, і збірка та тести впали в усіх. Межі між зонами трималися лише на домовленості. Окремо порожній `Cp1integration` з Docker-профілем Visual Studio вимагав WSL, а другий файл рішення `SmartArchiver.sln` без проєктів Data ламав відновлення пакетів і `dotnet build` з кореня.

**Варіанти.** (а) одна бібліотека з теками на зони; (б) окремий проєкт на кожну зону; (в) як (б), але формат окремо від тракту архіву.

**Рішення.** (б): Core (спільні типи), Compression, Security, Archive (формат і тракт), Data, Cli, App, і окремий тестовий проєкт на кожен. Compression залежить лише від Core, Security ні від кого, Archive — від Core і Security, CLI — від Archive і Data. Код перенесено через `git mv`, змінено лише namespace. `ArchiveSecurity` розділено: криптографічні примітиви лишилися в Security, а склейка з форматом томів (`Protect`, `Unprotect`, `BuildProtected`, `ReadProtected`) без змін перейшла в Archive як `ProtectedArchive`, інакше Security залежав би від формату. `Cp1integration` і `SmartArchiver.sln` видалено.

**Чому.** Межі зон збігаються з межами проєктів: видно, чия це робота, а компілятор не дає одній зоні залізти в нутрощі іншої. Поломка в зоні зачіпає лише її тести й тракт. У проєктах Compression і Security немає сторонніх пакетів, тож видно, що Гаффман і решта алгоритмів написані самостійно. (в) відкинуто: формат і тракт належать одній зоні й тісно пов'язані, а розділити їх можна пізніше.

## 15. Спільні налаштування збірки, центральні версії пакетів, лінтер

**Проблема.** Налаштування повторювалися в кожному `.csproj`, версії пакетів додавалися вручну і розходилися, EF Core тягнув `System.Security.Cryptography.Pkcs` 9.0.11 з відомими вразливостями (GHSA-846f-f764-76mx, GHSA-2fmv-rv2c-59x7), лінтера не було (критерій C4), а різні SDK та IDE давали різні, незрозумілі помилки.

**Варіанти.** (а) лишити налаштування в кожному проєкті; (б) винести їх у спільні файли й увімкнути лінтер.

**Рішення.** (б): `Directory.Build.props` (платформа, nullable, аналізатори .NET `latest-recommended` і правила стилю), `Directory.Packages.props` (усі версії пакетів, Pkcs закріплено на 10.0.13), `global.json` (SDK 10), `.editorconfig` (стиль і кодування), `tests/Directory.Build.props` (пакети тестів). У CI збірка йде з `-warnaserror`, локально попередження лишаються попередженнями. CA1707 вимкнено для `ErrorCode` (імена `E_*` задає методичка) і для імен тестів.

**Чому.** `.csproj` містять лише свої відмінності, нову версію пакета міняють в одному місці, і в усіх збирається те саме. Старий SDK одразу каже, що потрібен .NET 10. Лінтер, який не ламає CI, швидко перестають помічати, тож у CI попередження стають помилками.

## 16. Параметри захисту і розкладка захищеного тому

**Проблема.** Архів має бути зашифрований і автентифікований, але `FORMAT_SPEC_P2.md` команді не надали.

**Рішення.**
- PBKDF2-HMAC-SHA256: 100 000 ітерацій, 16-байтна випадкова сіль, 64 байти результату (32 для AES, 32 для HMAC).
- AES-256-CTR: 12-байтовий випадковий nonce, далі 32-бітний big-endian лічильник від 0.
- HMAC-SHA256: 32-байтовий тег від `header(41) || ciphertext`; перевіряється до розшифрування порівнянням за сталий час.
- Розкладка: `41-byte header | ciphertext | 32-byte HMAC`.
- Помилка перевірки автентичності — `E_HMAC`. Паролі й ключі в БД не записуються.

**Звірка.** Сумісність з еталонними архівами не підтверджена: розкладку й лічильник CTR потрібно звірити з `FORMAT_SPEC_P2.md`, коли він з'явиться.

# Рішення: Аналіз файлу (Blackcat-404), Чекпоінт 1

## 17. Точні визначення ознак файлу

**Проблема.** Методичка називає ознаки (ентропія, гістограма, частка друкованих символів, довжина рядків, автокореляція на лагах 1–16, ентропія біграм), але не визначає їх точно. Від визначень залежить, що бачитиме класифікатор, і що відповідати на захисті.

**Варіанти.** Друковані символи: лише `0x20…0x7E` чи разом з табуляцією й переходами рядка. Довжина рядка: рахувати `\r` чи ні. Автокореляція: сира коваріація чи нормована вибіркова автокореляція. Обсяг: увесь файл чи його частина.

**Рішення.**
- Ентропія: `H = −Σ p·log2 p` по 256 значеннях байта, від 0 до 8 біт.
- Гістограма: частота кожного значення байта, сума 1.
- Друковані: `0x20…0x7E`, `\t`, `\n`, `\r`; частка від усіх байтів.
- Середня довжина рядка: кількість символів без `\n` і `\r`, поділена на кількість рядків (останній рядок без `\n` теж рахується).
- Автокореляція: `r(k) = Σ(x[i]−m)(x[i+k]−m) / Σ(x[i]−m)²` для `k = 1…16`, від −1 до 1; для сталих даних або лагу, не меншого за довжину, `0`.
- Ентропія біграм: та сама формула по парах сусідніх байтів, від 0 до 16 біт.
- Ознаки рахуються по всьому файлу в пам'яті; потокове читання великих файлів — на CP2 разом із класифікатором.

**Чому.** Нормовані величини мають сталі межі, тож їх зручно подавати на вхід перцептрона. `\t`, `\n`, `\r` є в будь-якому тексті, а `\r` не враховується, щоб той самий текст з Windows і з Linux мав однакову довжину рядків. Кирилиця в UTF-8 займає два не-ASCII байти, тому в українському тексті частка друкованих ASCII близько 40%; це свідомо: ознака описує саме ASCII, а відрізнити такий текст від бінарних даних допомагають ентропія й автокореляція. Тести перевіряють ознаки на відомих даних (нулі, шум, текст), як радить методичка (10.41).

## 18. Будова перцептрона

**Проблема.** Потрібен власний багатошаровий перцептрон з навчанням і збереженням ваг (готові бібліотеки заборонені). На CP2 він класифікуватиме файли на 7 типів (`file_type` 0…6 з `FORMAT_SPEC_P2`).

**Варіанти.** Активація прихованих шарів: sigmoid, tanh, ReLU. Вихід: sigmoid з квадратичною помилкою чи softmax з cross-entropy. Збереження ваг: власний двійковий формат чи JSON.

**Рішення.** Довільна кількість шарів, у прихованих `tanh`, на виході `softmax`, помилка cross-entropy, навчання стохастичним градієнтним спуском із зворотним поширенням після кожного прикладу. Початкові ваги — рівномірні в межах `±√(6/(n_in+n_out))` з генератора із заданим seed, зсуви нульові. Ваги зберігаються в JSON через `System.Text.Json`. Правильність зворотного поширення перевіряється чисельним градієнтом, навчання — на XOR.

**Чому.** Softmax із cross-entropy природні для кількох класів і дають простий градієнт на виході `p − onehot(клас)`. `tanh` центрований навколо нуля і на маленьких мережах не має «мертвих» нейронів, як ReLU. Seed робить кожен запуск відтворюваним, а методичка вимагає порівнювати кілька ініціалізацій. JSON читається людиною, а `System.Text.Json` входить до .NET, тож сторонньої бібліотеки немає. Швидкість навчання для XOR виміряна: з `0.1` і 4 прихованими нейронами вчаться всі 30 перевірених seed, з `0.5` застрягає близько половини, тому тест використовує `0.1` і кілька seed.

# Рішення: База даних (Blackcat-404), Чекпоінт 2

## 19. Таблиці експериментів і обмеження цілісності

**Проблема.** На CP2 усі результати експериментів пишуться в БД: розбір потоку (жадібний, лінивий і ДП-розбір LZ77), пакування томів (ДП-рюкзак проти жадібного) і навчання класифікатора. Потрібна схема, з якої потім будуватимуться таблиці звіту, і шар доступу з параметризованими запитами, транзакціями та обмеженнями цілісності.

**Варіанти.** (а) одна таблиця з колонкою JSON для будь-яких результатів; (б) окрема таблиця з усіма полями журналу прогону для кожного експерименту; (в) спільна таблиця `Experiments` з полями журналу прогону і окремі типізовані таблиці результатів.

**Рішення.** (в). `Experiments` зберігає вид експерименту, дату, коміт, seed, набір даних і параметри. `ParsingResults`, `PackingResults` і `TrainingRuns` посилаються на неї зовнішнім ключем із каскадним видаленням. Види й методи зберігаються текстом (`Parsing`, `Greedy`, `Dp`…), а CHECK з переліком дозволених значень будується з самих C#-переліків. Обмеження CHECK додано і до нових, і до наявних таблиць: група 0–6 (`file_type` з `FORMAT_SPEC_P2`), розміри й час не від'ємні, `t_ref > 0`, використано не більше за місткість тому, macro-F1 від 0 до 1, епохи й швидкість навчання додатні, набір даних не порожній. Сховище отримало `SaveExperiment`, `GetExperiment` і `ListExperiments`.

**Чому.** JSON (а) не дає ні типів, ні CHECK, і з нього незручно будувати звіт. Окремі таблиці (б) повторювали б поля журналу прогону тричі. Спільна таблиця дає один журнал прогонів, а типізовані результати можна перевіряти базою. Обмеження в самій базі відхиляють неможливі значення навіть у разі помилки в коді, що пише результати. EF Core передає всі значення параметрами, тож текст на кшталт `x'; DROP TABLE Experiments; --` зберігається як звичайний рядок; це перевіряє тест. Експеримент разом з усіма результатами записується одним `SaveChanges`, тобто однією транзакцією: тест перевіряє, що експеримент, у якому один результат порушує CHECK, не зберігається зовсім.
