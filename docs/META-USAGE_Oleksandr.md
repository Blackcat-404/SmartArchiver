## 1. Отримання двох ключів за допомогою PBKDF2

**Задача.** Отримати з пароля два незалежні за призначенням 256-бітні ключі: для шифрування та для HMAC.

**Промпт (приклад запиту):**

> Як у C# реалізувати PBKDF2-HMAC-SHA256 із 100 000 ітерацій, 16-байтовою сіллю й результатом 64 байти? Як правильно розділити результат на два ключі по 32 байти?

**Відповідь / застосоване рішення:**

За допомогою `Rfc2898DeriveBytes.Pbkdf2` отримується 64-байтовий матеріал ключів. Перші 32 байти використовуються для AES-256, останні — для HMAC-SHA256. Сіль перевіряється на відповідність заданій довжині; тимчасовий буфер очищується.

```csharp
byte[] derived = Rfc2898DeriveBytes.Pbkdf2(
    password, salt, 100_000, HashAlgorithmName.SHA256, 64);
try
{
    return (derived[..32], derived[32..]);
}
finally
{
    CryptographicOperations.ZeroMemory(derived);
}
```

## 2. Шифрування та розшифрування AES-256-CTR

**Задача.** Побудувати CTR-режим поверх стандартного AES, оскільки шифрування та дешифрування мають працювати з однаковою функцією перетворення байтів.

**Промпт (приклад запиту):**

> Як реалізувати AES-256-CTR у .NET, використовуючи AES-ECB лише для генерації блоків ключового потоку? Як поєднати nonce з лічильником і не допустити переповнення?

**Відповідь / застосоване рішення:**

Для кожного 16-байтового блоку створюється лічильник: 12 байтів nonce та 4 байти номера блоку у форматі big-endian. AES шифрує цей лічильник; отриманий блок побітово додається XOR до вхідних даних. Застосування тієї самої операції до шифротексту відновлює початкові байти.

```csharp
for (long block = 0; block < blocks; block++)
{
    BinaryPrimitives.WriteUInt32BigEndian(counter[12..], (uint)block);
    aes.EncryptEcb(counter, streamBlock, PaddingMode.None);

    int offset = checked((int)(block * 16));
    int take = Math.Min(16, input.Length - offset);
    for (int i = 0; i < take; i++)
        result[offset + i] = (byte)(input[offset + i] ^ streamBlock[i]);
}
```

**Уточнення.** Порядок байтів і початкове значення лічильника в наявній реалізації є робочим узгодженням; перед підтримкою еталонних архівів їх слід звірити з `FORMAT_SPEC_P2.md`.

## 3. Контроль цілісності через HMAC-SHA256

**Задача.** Виявляти зміну заголовка чи шифротексту та не розшифровувати дані до перевірки автентичності.

**Промпт (приклад запиту):**

> Як у C# обчислювати HMAC-SHA256 для заголовка та шифротексту? Як перевіряти тег без звичайного порівняння масивів, щоб час порівняння не залежав від першого неправильного байта?

**Відповідь / застосоване рішення:**

HMAC обчислюється окремим 32-байтовим ключем. Під час читання архіву спочатку перевіряється тег, а лише потім запускається AES-CTR. Для порівняння застосовується `CryptographicOperations.FixedTimeEquals`.

```csharp
public static byte[] ComputeTag(
    ReadOnlySpan<byte> message, ReadOnlySpan<byte> authenticationKey) =>
    HMACSHA256.HashData(authenticationKey, message);

// Фрагмент перевірки:
byte[] expected = ComputeTag(message, authenticationKey);
try
{
    return CryptographicOperations.FixedTimeEquals(expected, tag);
}
finally
{
    CryptographicOperations.ZeroMemory(expected);
}
```

## 4. Захист архіву без зміни решти модулів

**Задача.** Додати шифрування до наявного `SmartArchiver.Core`, не переписуючи `ArchiveWriter`, `ArchiveReader`, базу даних чи графічний інтерфейс Avalonia.

**Промпт (приклад запиту):**

> У проєкті вже працюють ArchiveWriter і ArchiveReader для SARC. Як додати окремий клас захисту, який приймає готовий архів, шифрує payload і передає розшифрований архів назад існуючому читачу?

**Відповідь / застосоване рішення:**

Створено окремий клас `ArchiveSecurity` у `SmartArchiver.Core`. Методи `Protect` і `Unprotect` виконують криптографічні операції, а обгортки `BuildProtected` та `ReadProtected` викликають наявні модулі архівації. Це залишає можливість підключити захист до CLI та Avalonia окремим етапом інтеграції.

```csharp
public static byte[] BuildProtected(
    IReadOnlyList<ArchiveInput> files, string password,
    int blockSize = FormatConstants.DefaultBlockSize) =>
    Protect(new ArchiveWriter(blockSize).Build(files), password);

public static IReadOnlyList<ExtractedFile> ReadProtected(
    byte[] archive, string password) =>
    ArchiveReader.Read(Unprotect(archive, password));
```

**Обмеження:** на CP1 ця обгортка обробляє один том; підключення багатотомного захисту та перевірка відповідності еталонному формату залишаються окремими інтеграційними завданнями.

## 16. Повний тракт як функція пристосованості

**Задача.** Оцінювати конфігурацію архіватора за результатом роботи всієї системи, включно зі швидкістю та перевіркою відновлення файлів.

**Промпт (приклад запиту):**

> Підключи генетичний алгоритм до повного тракту SmartArchiver. Для кожної хромосоми запакуй корпус, зашифруй томи, розпакуй їх і перевір побайтове відновлення. Використай наявну метрику Q.

**Відповідь / застосоване рішення:**

Підготовлено окремий проєкт `SmartArchiver.Optimization` і компонент `CorpusFitnessEvaluator`. Базова оцінка використовує `CorpusMeasurer` та `ArchivePipeline`: аналіз → блоки → LZ77 → Гаффман → пакування томів → шифрування → перевірка та розпакування. Параметри стиснення передаються через `PackOptions` і `Lz77SearchOptions`.

```text
S = B_orig / (B_orig + B_arc)
T = t_ref / (t_ref + t)
Q = α·S + β·T
```

Якщо хоча б один файл не відновлюється, пристосованість дорівнює нулю. Розмір архіву враховує захищені томи. Ваги α, β, опорний час і місткість тому беруться з командної конфігурації; без неї застосовуються наявні типові значення.

## 17. Генетичний алгоритм із трьома генами

**Задача.** Реалізувати хромосому з вікном пошуку, мінімальною довжиною збігу та порогом відмови від стиснення.

**Промпт (приклад запиту):**

> Реалізуй ГА на C#: три гени параметрів LZ77, турнірна селекція, кросовер, мутація та елітизм. Параметри мають реально впливати на стиснення.

**Відповідь / застосоване рішення:**

Додано `BasicChromosome`, `BasicChromosomeSpace` та `GeneticAlgorithm<T>`. Для базових генів використано рівномірний кросовер. Турнір обирає батьків за пристосованістю, мутація змінює гени в допустимих межах, еліти переходять у наступне покоління.

| Ген | Реалізований зміст |
| --- | --- |
| `window` | Вікно пошуку LZ77; простір пошуку містить 256, 512, 1024, 2048, 4096, 8192, 16384 і 32768 байтів |
| `min_match` | Мінімальна довжина посилання, від 3 до 258 байтів |
| `abandon_threshold` | Мінімальна частка економії для збереження стисненого блока; у випадковій генерації та мутації — від 0 до 0.25 із кроком 0.01 |

Для застосування генів параметризовано пошук збігів і парсери Greedy, Lazy, DP та Iterative. Поріг `0.05` означає, що стиснений блок зберігається лише за економії щонайменше 5%, якщо дозволено сирі блоки. Формат декодування LZ77 залишається сумісним.

## 18. ГА проти випадкового пошуку — D1 №17

**Задача.** Порівняти пошуки за однакового числа обчислень пристосованості та перевірити збереження найкращого результату.

**Промпт (приклад запиту):**

> Додай випадковий пошук з таким самим бюджетом fitness-викликів, як у ГА. Перевір, що найкраще значення останнього покоління не гірше за значення нульового покоління.

**Відповідь / застосоване рішення:**

Додано `RandomSearch<T>`. Обидва алгоритми оцінюють `PopulationSize × (Generations + 1)` хромосом, включно з початковою популяцією. Повторне оцінювання еліт також входить до бюджету. Для еліти зберігається краща з попередньої та повторної оцінок, що забезпечує незменшення збереженого найкращого значення за наявності елітизму. Оскільки Q залежить від виміряного часу, повторні оцінки можуть відрізнятися.

```text
best(last_generation) >= best(generation_0)
```

Додано тест на рівність бюджетів і цю умову на синтетичній функції. Проходження D1 №17 на реальному корпусі потребує запуску. Рівність бюджетів сама по собі не доводить переваги ГА над випадковим пошуком.

## 19. Повна хромосома та локальний пошук

**Задача.** Розширити хромосому параметрами інших етапів і додати другий кросовер, адаптивну мутацію та порівняння з локальним пошуком.

**Промпт (приклад запиту):**

> Додай глибину пошуку збігів, розмір блока Гаффмана, історію k, архітектуру перцептрона і прапорці стратегій. Реалізуй двоточковий кросовер, адаптивну мутацію та локальний пошук.

**Відповідь / застосоване рішення:**

Додано `FullChromosome` і `FullChromosomeSpace`. Повна хромосома має вісім генів, включно з трьома базовими. Для неї використано двоточковий кросовер.

| Додатковий ген | Реалізація |
| --- | --- |
| `search_depth` | Від 1 до 1024 перевірених кандидатів хеш-ланцюжка |
| `huffman_block_size` | Незалежні блоки 4, 8, 16, 32 або 64 КіБ |
| `history_k` | Від 1 до 4 попередніх байтів для прогнозу |
| `perceptron_architecture` | Compact, Standard або Wide: прихований шар із 16, 32 або 64 нейронів |
| `strategy_flags` | Класифікатор, прогноз байта, стратегія по блоках, DP/Iterative-парсер, DP-пакування, дозвіл сирих блоків |

Імовірність мутації зменшується протягом поколінь і підсилюється після застою. `LocalSearch<T>` виконує пошук першого покращення серед сусідніх конфігурацій; у CLI він стартує з найкращої хромосоми ГА, тому це перевірка можливості її додаткового покращення.

Для прогнозу модель детерміновано навчається та кешується за парою «k, архітектура». Час навчання не входить до T; час кодування залишків і їх відновлення входить. Модель навчається на тому самому корпусі, тому оцінка не характеризує якість на незалежних даних. Прогноз реалізовано як експериментальне перетворення з подальшим відновленням тим самим об'єктом моделі; самодостатній формат архіву для довільної навченої моделі цією роботою не реалізовано.

## 20. Фронт Парето за стисненням і швидкодією

**Задача.** Показати компроміси між розміром архіву та часом роботи.

**Промпт (приклад запиту):**

> Збережи S і T кожної конфігурації окремо та виділи недоміновані точки: інша конфігурація не повинна бути кращою за обома критеріями одночасно.

**Відповідь / застосоване рішення:**

Додано `ParetoFront.Compute` та `ReportTables.ParetoFront`. Конфігурація домінує іншу, якщо її S і T не менші та хоча б один критерій строго більший. Обидва критерії максимізуються: більше S означає менший архів за сталого оригінального розміру, більше T — менший час за сталого t_ref.

**Межа реалізації:** фронт виділяється серед уже оцінених конфігурацій ГА, випадкового й локального пошуку. Сам пошук ГА оптимізує скалярне Q. Окремий багатокритеріальний еволюційний алгоритм із селекцією за домінуванням, наприклад NSGA-II, не реалізовано; експертну вимогу багатокритеріального пошуку повністю закритою вважати не можна.
